# Input-Mapping Configuration & Remapping UX for a DualShock4-to-CATIA-V5 Application

## What config file format should the profile system use (JSON/YAML/TOML/XML/INI), and what are the pros/cons for this use case?

### Takeaway
Existing remapping tools split between XML (AntiMicroX), INI/custom text (JoyToKey), and Valve's KeyValues/VDF (Steam Input); none of the gaming-input tools surveyed use YAML or TOML natively, but general config-format guidance strongly favors TOML or YAML over raw JSON when the file must be hand-edited, commented, diffed in git, and shared between non-technical users — JSON's lack of comments is the single biggest practical disqualifier for a user-facing profile format.

### Cited Findings
- AntiMicroX saves profiles as `.amgp` files, which are XML; a user who tried to hand-edit them reported "I've looked at the .amgp profile files now supported by AntiMicroX using a text editor. In theory it might be possible for me to edit those, but the xml format isn't easy to work with." — [AntiMicroX GitHub](https://github.com/AntiMicroX/antimicroX)
- AntiMicroX's community-profile repo organizes profiles hierarchically as `applications/<APPLICATION>/<Controller UniqueID or GUID>/<PROFILE>`, with most profiles keyed to the generic SDL Game Controller GUID `sdlgamecontroller` so one profile works across many physical pads — [AntiMicroX profiles README](https://raw.githubusercontent.com/AntiMicroX/antimicrox/master/README.md)
- JoyToKey stores global settings in `JoyToKey.ini` and per-game button mappings in separate `.cfg` files; as of v5.4.1 these were switched to "UTF8+BOM" encoding specifically to fix garbled non-English text, and simple numeric settings like `AnalogDeadZone` (range 0–10000, default 1000) are documented as directly hand-editable in the ini — [JoyToKey changelog via Softpedia](https://games.softpedia.com/progChangelog/JoyToKey-Changelog-140221.html)
- reWASD's on-disk unit is a `.rewasd` file described by the vendor forum as JSON-style, containing a `schemaVersion`, `appVersion`, and a `config` block with `appName`, `comment`, `minTimeUnit`, `description`, followed by a `devices` list (this is a forum-posted example, not official schema docs, so treat the exact field names as illustrative rather than authoritative) — [reWASD community config post](https://www.rewasd.com/community/config/59e1e8aef2a98ca0a2a6f5a4531a4238)
- Steam's in-game-action (IGA) files, which define the default action sets/layers Steam Input binds against, are written in Valve's **KeyValues (VDF)** format, a nested `"key" { }` text format — [Steamworks IGA file doc](https://partner.steamgames.com/doc/features/steam_controller/iga_file); a real example (for the game Tallowmere 2) shows a top-level `"actions"` block with named action sets (e.g. `SteamInputControls`) and nested per-button action entries — [ChrisNZL IGA gist](https://gist.github.com/ChrisNZL/aba43315ead8e049c28d1dce01ded57c)
- Unity's Input System stores its action-binding asset (`.inputactions`) as **plain JSON** on disk; the API explicitly supports round-tripping via `LoadFromJson(string)` and `ToJson()`, and the asset contains action maps, actions, bindings, and control schemes, with composite bindings (e.g. a 2D-vector composite built from 4 buttons) represented as a parent binding entry plus one child entry per part — [Unity InputActionAsset docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.0/api/UnityEngine.InputSystem.InputActionAsset.html), [Input Action Assets manual](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.0/manual/ActionAssets.html)
- Godot's `InputMap` is configured via `ProjectSettings` (`input/*` keys) or in code, with a per-action deadzone set via `action_set_deadzone(action, deadzone)` / `add_action(action, deadzone=0.2)`; defaults changed between Godot versions (0.5 in 4.2 docs, 0.2 in 4.4/4.5 docs) — [Godot InputMap class docs (4.5)](https://docs.godotengine.org/en/4.5/classes/class_inputmap.html). I could not confirm the exact on-disk key layout inside `project.godot` for an action (this is a **gap**, see below).
- General format comparison (not input-remapping-specific, but directly relevant to the "human-editable/commentable" requirement): JSON has no comment support at all ("that is not in the spec"), which several independent write-ups call a disqualifier for human-maintained config; YAML and TOML both support `#` comments — [devtoolbox.dedyn.io comparison](https://devtoolbox.dedyn.io/blog/json-vs-yaml-vs-toml)
- The same source notes JSON has by far the most mature tooling ecosystem (schema validation via JSON Schema, diff tools, universal parsers) while TOML's tooling is "a clear weak spot," and flags a real-world YAML footgun: an Ansible playbook broke because a line read `country: NO`, which YAML's implicit typing silently coerced to boolean false — [devtoolbox.dedyn.io comparison](https://devtoolbox.dedyn.io/blog/json-vs-yaml-vs-toml)
- Common real-world precedent: TOML is the standard for `Cargo.toml`/`pyproject.toml`; YAML is standard for CI/CD and Kubernetes manifests; JSON is standard for `package.json`/`tsconfig.json` — [devtoolbox.dedyn.io comparison](https://devtoolbox.dedyn.io/blog/json-vs-yaml-vs-toml)

### Inferences
- No major gaming-input tool in this survey actually ships YAML or TOML profiles — the ecosystem norm is XML (AntiMicroX), custom INI/CFG (JoyToKey), KeyValues/VDF (Steam), or raw JSON (Unity, reWASD's apparent format). This suggests the "best" format from a general-software-engineering standpoint (YAML/TOML, for comments + diffability) is not what end users of this product category expect to see if they ever open the file; a JSON-based format with a schema-validated structure (JSON Schema) would fit the ecosystem norm (Unity does this) and gets the best tooling, at the cost of comments — which can be mitigated by generating the file only through the GUI and treating "advanced/raw edit" as a secondary, developer-facing feature rather than the primary workflow.
- For a CATIA-focused tool aimed partly at engineers (who are comfortable with structured text files, e.g. CATIA's own macros/VBA) but who are not software developers, **JSON with a published JSON Schema** (for IDE/editor validation and autocompletion) is a reasonable middle ground: it matches the Unity precedent most closely among the surveyed prior art, is trivially diffable/mergeable in git for sharing profiles, and avoids YAML's implicit-typing footguns that would be especially dangerous for numeric deadzone/sensitivity values. If hand-editing comments is considered essential, TOML is the next-best option (better readability + comments than JSON, less error-prone implicit typing than YAML) but has no precedent in this specific tool category and weaker tooling.
- Profile portability/sharing between users (explicitly requested in the UX question) strongly favors a single self-contained file (JSON/TOML/XML) over a multi-file INI-per-profile scheme like JoyToKey's, since a single file is trivially shareable as an attachment or gist and diff/mergeable, matching how AntiMicroX's community-profile GitHub repo and the Steam IGA/gist examples are shared.

### Gaps
- No official, field-by-field AntiMicroX `.amgp` XML schema was found in search results (only the repo's organizational README); the actual element names for buttons/axes/sensitivity/deadzone inside an `.amgp` file were not retrieved (a direct fetch of a sample profile file 404'd). This would need a direct read of a real `.amgp` file from the AntiMicroX source or installed app rather than web search.
- No official JoyToKey schema/field reference for the main per-button mapping syntax in `.cfg` files was found (only a changelog entry about a hold/multi-tap feature and the `AnalogDeadZone` ini key); the "default"/common-case line format was not confirmed from an official source.
- The exact on-disk representation of Godot's per-action deadzone/events inside `project.godot` was not confirmed from documentation (only the runtime API was documented); treat any sample as illustrative only.
- No direct, official reWASD schema documentation (only a third-party forum post showing one example structure) was found; the full set of fields in `.rewasd` files is unconfirmed.
- No sources specifically comparing git-diff/merge friendliness of JSON vs. YAML vs. TOML vs. XML for *controller-profile* files were found; the general config-format comparison found is a reasonable proxy but not input-remapping-specific.

## What schema design works for a single binding, a profile grouping many bindings, and automatic profile switching based on detected application context (e.g. active CATIA workbench)?

### Takeaway
The most mature, well-documented precedent for the binding/profile schema layer is Unity's Input System (action maps → actions → bindings, with explicit composite bindings for multi-part inputs and a documented deadzone/processor model) combined with Steam Input's "action set" / "action set layer" concept for context switching; for CATIA-specific auto-switching, COM automation exposes a documented `GetWorkbenchId`-style call that returns a stable internal workbench identifier (e.g. `"PrtCfg"` for Part Design, `"GPSCfg"` for Generative Structural Analysis) that is more robust to detect than parsing the window title.

### Cited Findings
- Unity's Input System asset structure is: an `InputActionAsset` contains multiple **action maps**; each action map is "a collection of Actions that you can enable or disable in bulk"; each **action** has one or more **bindings**; **composite bindings** combine multiple physical controls into one logical control (the documented example: a 2D-Vector composite built from four separate button bindings for up/down/left/right) — [Unity Input Action Assets manual](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.0/manual/ActionAssets.html), [InputActionAsset API docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.0/api/UnityEngine.InputSystem.InputActionAsset.html)
- Unity's asset is plain JSON on disk and supports `LoadFromJson`/`ToJson` round-tripping; critically, "all action maps in an asset share binding state," meaning multiple maps can be defined once but swapped/enabled independently — a useful separation between "the library of all possible bindings" and "which map is currently active" — [Unity InputActionAsset API docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.0/api/UnityEngine.InputSystem.InputActionAsset.html)
- Steam Input's **action set layers** are the documented mechanism for context-dependent remapping on top of a base profile: a layer "draw[s] their actions from the Action Set they exist within and do not wholesale replace what is already active when applied, but apply small modifications"; activating a *new base action set* clears all active layers from the old set automatically; activating a layer that's already active is a no-op — [Steamworks Action Set Layers doc](https://partner.steamgames.com/doc/features/steam_controller/action_set_layers) (note: this specific partner.steamgames.com page could not be re-fetched directly in this session due to network restrictions — findings here are from the search-result summary of that page, not a full-page read)
- Steam's API separately exposes `DeactivateAllActionSetLayers` (reset) and `GetActiveActionSetLayers` (query which layers are currently stacked on a controller handle) — [ISteamInput API reference, via search summary](https://partner.steamgames.com/doc/api/isteaminput)
- Steam's own guidance explicitly recommends layers as the mechanism for "similar modes" rather than defining a whole separate action set per mode — directly analogous to a "per-CATIA-workbench" mode design — [Steamworks Action Set Layers doc, via search summary](https://partner.steamgames.com/doc/features/steam_controller/action_set_layers)
- The underlying Steam config format for default bindings is Valve's KeyValues/VDF "in-game actions" (IGA) file; its "Action Manifest" file maps a controller type to a specific VDF path per configuration, e.g. `"configurations" { "controller_xboxone" { "0" { "path" "xbox_controller.vdf" } } }` — [Steamworks Action Manifest doc, via search summary](https://partner.steamgames.com/doc/features/steam_controller/action_manifest_file)
- Godot's `InputMap` binds a deadzone **per action** (not globally), via `action_set_deadzone(action: StringName, deadzone: float)` / `add_action(action, deadzone=0.5 or 0.2 depending on version)`, and documents deadzone semantics as "how much a joypad stick (or trigger) needs to be moved before the action is considered pressed" — [Godot InputMap class docs](https://docs.godotengine.org/en/4.5/classes/class_inputmap.html), [Godot axis-mapping article](https://godotengine.org/article/handling-axis-godot/)
- For CATIA context detection: pycatia's mirror of the CAA V5 Visual Basic help documents a `GetWorkbenchId` function on the `Application` object returning the identifier string of the current workbench, and a separate `ActiveWindow` read-only property on the application object representing "the window in which the end user is currently editing the active document" — [pycatia application.html docs, via search summary](https://pycatia.readthedocs.io/en/latest/api/pycatia/in_interfaces/application.html) (direct fetch of this page failed due to network restrictions in this session; relying on the search-result summary only)
- A forum example calls this as `CATIA.GetWorkbenchID`, stores it in a string, and compares it (via `Cstr`) against known IDs — one confirmed real ID is `"PrtCfg"` for Part Design — to branch logic — [Eng-Tips forum thread](https://eng-tips.com/threads/some-questions-about-macro-programing.408234)
- A separate, confirmed real workbench ID is `"GPSCfg"`, used with `CATIA.StartWorkbench "GPSCfg"` to switch into the Generative Structural Analysis workbench (shown in an IBM support bug note, so the ID itself is real even though the note describes a bug in workbench-switching, not detection) — [IBM Support note](https://ibm.com/support/pages/apar/HD62000)
- `ActiveDocument.GetWorkbench("SPAWorkbench")` is a *different*, document-level call returning a workbench *object* (not a plain ID string), so implementers must be careful not to conflate it with `Application.GetWorkbenchId` — [Eng-Tips forum thread](https://eng-tips.com/threads/some-questions-about-macro-programing.408234)
- No source found that reads the active workbench from the CATIA window title directly; window titles were described in search results as reflecting the open *document* name, not the workbench, so COM/automation (via `GetWorkbenchId`) is the documented/reliable route rather than title-string parsing (window-title / UI Automation polling was not documented as a supported CATIA detection method in any source found).

### Inferences
- A clean three-layer schema, combining the Unity and Steam precedents, is: **(1) Binding** = one physical input (with per-binding modifiers like deadzone/sensitivity/curve for analog, and tap-vs-hold timing for digital) → one target action; **(2) Profile/Action-Map** = a named, complete set of bindings for a "mode" (directly analogous to Unity's action map or Steam's base action set) — e.g. one profile per CATIA workbench (Part Design, Assembly Design, Sketcher, Drafting, GSD); **(3) Layer** = a Steam-style partial overlay activated by holding a shift/modifier button (e.g. L1), which only overrides specific bindings within the *currently active* profile rather than replacing it wholesale, and which is automatically cleared whenever the active profile itself changes (mirroring Steam's rule that switching the base action set clears all active layers) — this cleanly separates "which CATIA workbench am I in" (profile switch, context-driven) from "what am I holding right now" (layer, momentary user-driven).
- Because a reliable, documented COM call (`GetWorkbenchId`) exists for CATIA, the architecture should poll (or, if CATIA's automation model exposes an event, subscribe to) the active CATIA `Application` object's `GetWorkbenchId`/`ActiveDocument` rather than rely on window-title text parsing or UI Automation, which is undocumented and fragile for workbench detection specifically (window titles track the open document, not the active workbench). A fallback title-based heuristic could still be kept as a degraded-mode detector when COM access is unavailable (e.g. CATIA running elevated, or automation disabled), but it should not be the primary mechanism.
- A profile-switch confirmation/debounce is advisable: since workbench changes inside CATIA can be rapid (e.g. opening a dialog, switching tabs), the context-detection poll should debounce short-lived or transient `GetWorkbenchId` changes before swapping the active controller profile, to avoid "profile flapping" during normal CATIA use.

### Gaps
- No source documented the exact polling/eventing model for `GetWorkbenchId` (i.e., whether CATIA fires a COM event on workbench change, versus requiring the client to poll); this is a meaningful open implementation question — polling-based detection carries a latency/CPU tradeoff not addressed in any source found.
- No complete ID→display-name table for all CATIA V5 workbenches (Part Design, Assembly Design, Sketcher, Drafting, Generative Shape Design) was found; only `PrtCfg` (Part Design) and `GPSCfg` (Generative Structural Analysis, not Generative Shape Design) were confirmed. The Sketcher, Assembly Design, Drafting, and Generative Shape Design internal IDs were not found and would need to be captured empirically (e.g. by instrumenting `GetWorkbenchId` while switching workbenches in a live CATIA session) or sourced from the CAA V5 Visual Basic / V5Automation reference documentation directly.
- The full, official Steam Input action-set-layer activation API (`ActivateActionSetLayer`) signature was not retrieved (the deprecated `ISteamController` equivalent was mentioned in search results but not the current `ISteamInput` method); exact parameter shape is unconfirmed.
- No source addressed nested/inherited profiles (e.g. a "base" profile with workbench-specific profiles inheriting common bindings and only overriding deltas) in any of the surveyed tools' schemas — this is a gap in prior art, not just in search coverage; none of AntiMicroX, JoyToKey, reWASD, Steam Input, Unity, or Godot documentation surfaced an explicit "profile inheritance" feature. This should be treated as a design decision without strong precedent rather than an established pattern.

## How do existing tools (AntiMicroX, JoyToKey, Steam Input, reWASD, Unity Input System, Godot Input Map) handle live-capture binding, chords/combos, layers/shift-states, and in-UI preview/testing?

### Takeaway
Live "press-to-bind" capture is a near-universal UX pattern but implementations diverge on input filtering, consuming vs. leaking the raw input to the underlying app, and conflict handling; shift/layer systems are the dominant answer to "more actions than physical buttons" (reWASD documents up to 10 overlay layers with Hold/Toggle/Custom activation), while explicit in-UI live preview/testing was the weakest-documented area across all tools surveyed.

### Cited Findings
- reWASD's **Shift mode** lets users create overlays ("up to 10 overlays," since reWASD 6.4) whose bindings differ from the Main layer; the "Jump to Shift" trigger can be configured as **Hold**, **Toggle**, or **Custom**; in Custom mode, separate buttons can be bound to exit the shift layer or jump to a *different* shift layer, and the docs warn that if "Jump to Layer 0 (Main)" isn't set, the user gets stuck in the shift layer until the config is reapplied; any control with no explicit shift-layer mapping simply falls back to its Main-layer behavior, and there's a "Do not inherit" option to force a control to behave normally even while a shift layer is active — [reWASD Shift Mode help page, via search summary](https://help.rewasd.com/basic-functions/shift-mode.html) (direct fetch of this page failed in this session due to network restrictions; based on the search-result summary only)
- A reWASD user forum thread requests a **"Global shift layer"** feature, implying the current implementation ties shift layers to a specific device/profile rather than offering one global layer across profiles — [reWASD forum thread #230002](https://forum.rewasd.com/forum/rewasd/suggestions-aa/230002-global-shift-layer)
- A reWASD forum post on single-button-press capture reports that capture "only worked when 'Hook controller buttons' was enabled and remap was not currently active," which the poster called non-obvious UI behavior — i.e., live-capture mode and "hook" (pass-through suppression) mode are coupled toggles that must both be in the right state for binding capture to work reliably — [reWASD forum, remapping explicit option thread, via search summary](https://forum.rewasd.com/forum/rewasd/suggestions-aa/246498-remapping-explicit-option-to-record-single-button-press)
- JoyToKey supports a **tap-count / hold-duration disambiguation** feature at the button level: a single physical button can be aliased to switch between two *other* button identities "based on the button hold duration or based on how many times it's pressed" (documented example: `Input1=Button31`, `Input2=Button32`) — this is JoyToKey's mechanism for tap-vs-hold and multi-tap distinction without a separate "layer" concept — [JoyToKey changelog, via search summary](https://games.softpedia.com/progChangelog/JoyToKey-Changelog-140221.html)
- Unity's Input System ships an official **"Rebinding UI" sample** (installable via Package Manager) built around `StartInteractiveRebind()`/`PerformInteractiveRebind()`, which starts a rebind operation that waits for the next control press; the sample's `RebindActionUI` component is described as "an optional overlay that appears when a rebind starts," and each rebind returns a disposable `RebindingOperation` object — [Unity InputActionRebindingExtensions.RebindingOperation docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.9/api/UnityEngine.InputSystem.InputActionRebindingExtensions.RebindingOperation.html)
- A **real, filed Unity bug** documents a concrete pitfall of live-capture UX: "input system interactive binding does not fully suppress controller inputs when pressing action button" — i.e., during a rebind-capture flow, the control being pressed to *assign* a new binding wasn't being suppressed from also *triggering* the old binding, surfacing a spurious "INPUT DETECTED!!" in the running game — a documented, real-world argument for making the capture step consume/swallow the raw input rather than let it pass through — [Unity Issue Tracker](https://issuetracker.unity3d.com/issues/input-system-interactive-binding-does-not-fully-suppress-controller-inputs-when-pressing-action-button)
- An Orx engine tutorial's remap routine filters captured input strictly by device type (accepts only joystick-button events, explicitly ignoring keyboard/mouse during a joystick rebind) before committing the new binding — a concrete, documented pattern for input-type filtering during capture — [Orx remapping-inputs wiki tutorial, via search summary](https://wiki.orx-project.org/en/tutorials/input/remapping_inputs)
- Console-vendor UX precedent for capture-and-confirm flows: Xbox's documented flow is press-and-hold the source button to enter remap, then press the target button to complete the remap; SteelSeries documents a two-step press-then-confirm flow where a dedicated Menu button confirms each binding step — [GamesRadar on Xbox remapping](https://gamesradar.com/xbox-one-button-mapping-comes-normal-controllers), [SteelSeries support article, via search summary](https://support.steelseries.com/hc/en-us/articles/48459302766861-How-do-I-remap-buttons-on-my-Aeon-Pro-controller)
- Steam Input's **action set layers** (already covered in Q2) are the documented mechanism closest to a "shift state": a layer is authored almost identically to a regular action set ("You create action set layers almost exactly like regular action sets. You click 'Add Action Layer' in the configurator"), and multiple layers can be stacked on a base action set simultaneously — [Steamworks Action Set Layers doc, via search summary](https://partner.steamgames.com/doc/features/steam_controller/action_set_layers)
- No source found describes a dedicated **live preview/dry-run testing panel** (e.g. a controller diagram that highlights which zone is currently pressed, decoupled from actually sending the mapped output) in any of AntiMicroX, JoyToKey, reWASD, Steam Input, Unity, or Godot's documented UI — this absence itself is notable and is called out as a Gap below rather than asserted as a finding.

### Inferences
- The strongest, most battle-tested design for "more actions than physical buttons" across the surveyed tools is a **hold-to-shift layer stack** (reWASD's model, mirrored conceptually by Steam's action-set layers): a designated button (natural choice on DS4: **L1** or a dedicated function button, since L2/R2/R1 are often needed for primary CAD actions like rotate/zoom) held down swaps the *meaning* of every other control to a secondary mapping, falling back to the base/Main mapping for any control with no shift-specific override. This directly solves the "many more mappable actions than physical buttons" requirement without inventing a new UX pattern.
- Because the Unity bug report shows that failing to suppress raw input during capture is a real, documented failure mode, the CATIA tool's "press any button to bind" flow must explicitly swallow the DS4 input event during capture (not forward it to CATIA as a live command) — otherwise a user capturing, say, the Cross button could simultaneously trigger whatever Cross is *currently* bound to inside CATIA.
- reWASD's documented gotcha (capture only works when "Hook controller buttons" is enabled and no remap is active) suggests the capture UI needs a clearly visible "listening..." state indicator and should temporarily disable the live remap/output engine while capture is in progress, to avoid exactly this class of user confusion.
- The complete absence of a documented "live preview without leaving the config UI" feature across all six surveyed tools suggests this is a genuine UX gap in the category — building one (e.g., a small overlay/panel showing real-time DS4 input state next to the binding editor, as a logging/diagnostic view rather than a full test harness) would be a differentiating feature rather than table-stakes parity with existing tools.
- JoyToKey's tap-count/hold-duration button-aliasing and reWASD's Hold/Toggle/Custom shift-activation modes together suggest that "hold vs. tap" distinction should be a per-binding *or* per-layer-trigger configurable property (at minimum: tap threshold in ms, and a toggle-vs-hold-to-sustain choice for the layer/shift button itself), not a single global setting.

### Gaps
- No tool's documentation (in the sources retrieved) specifies an exact chord/combo syntax (e.g. "L1 + Cross = Action A" as a single atomic binding, independent of a layer/shift system) — reWASD's shift-layer model and Steam's action-set-layer model both achieve combo-like behavior by *redefining a button while another is held*, which is functionally a chord, but no source documented a tool offering true simultaneous multi-button chord bindings (e.g., "this exact single action fires only if both L1 and R1 are pressed within X ms of each other, independent of any shift-layer redefinition"). This is a gap in available documentation, not necessarily an absence in the tools themselves — AntiMicroX in particular is known in the community to support multi-key/modifier-style bindings, but this was not confirmed via search in this session.
- No source documented how any tool (AntiMicroX, JoyToKey, Steam Input, reWASD) implements an in-app "test my mapping" / live preview panel; this entire sub-question returned no positive findings, only its absence.
- Exact AntiMicroX capture-binding UX (its own "press any button" flow details) was not retrieved from search results in this session — only general/other-tool capture patterns were found; a direct read of the AntiMicroX wiki's remapping page (not retrieved here due to time/call budget) would close this gap.

## What UX patterns make remapping approachable for non-technical users, versus what should be reserved for an "advanced"/raw config mode?

### Takeaway
Across the surveyed tools and UX discussion threads, approachable remapping consistently centers on visual, click-to-bind controller diagrams and guided capture-and-confirm flows, while raw file editing is treated by every tool's own docs as a secondary/power-user path (explicitly flagged as hard to use even by AntiMicroX's own user base); conflict handling, clear capture/"listening" state, and input-type filtering are the recurring approachability concerns, not just binding selection itself.

### Cited Findings
- AntiMicroX's own `.amgp` XML profile format was independently called hard to work with by a user attempting manual edits ("the xml format isn't easy to work with") — direct evidence that even power users route around raw file editing in favor of the app's UI when possible — [AntiMicroX GitHub](https://github.com/AntiMicroX/antimicroX)
- Console/peripheral vendors converge on a **capture-then-confirm** two-step flow for non-technical remap UX: Xbox's documented pattern is press-and-hold the source control, then press the desired target control; SteelSeries uses an explicit two-step press-then-confirm with a dedicated confirm (Menu) button — both patterns remove ambiguity about when a binding "took" — [GamesRadar on Xbox remapping](https://gamesradar.com/xbox-one-button-mapping-comes-normal-controllers), [SteelSeries support, via search summary](https://support.steelseries.com/hc/en-us/articles/48459302766861-How-do-I-remap-buttons-on-my-Aeon-Pro-controller)
- Developer discussion (itch.io) on remap UX flags two concrete non-technical-user pitfalls worth designing around explicitly: (1) whether to silently overwrite an existing binding when the user captures a control already in use elsewhere, versus warn/second-press-to-confirm; and (2) the need to explicitly exclude certain "reserved" keys (the example given was Backspace, used as a "clear this binding" action) from the set of capturable/bindable inputs, so the app doesn't let a user accidentally bind over its own UI controls — [itch.io dev posts, via search summary](https://itch.io/post/2127104), [itch.io dev posts, via search summary](https://itch.io/post/2130757)
- reWASD's own help docs describe Shift Mode (the layer system) with explicit safety language around users getting "stuck" in a shift layer if they don't configure a return-to-Main trigger — direct evidence that layered/advanced features, even in a GUI tool, need built-in guardrails (reWASD mitigates by falling back any un-mapped control to Main-layer behavior by default) — [reWASD Shift Mode help page, via search summary](https://help.rewasd.com/basic-functions/shift-mode.html)
- A browser-based capture caveat worth carrying into a Windows-only context by analogy: the Gamepad API (used by browser-based testers) requires an initial user gesture before input can even be read, illustrating that "listening for input" states have real platform-level preconditions that the UI must account for (e.g., a visible "press a button now" prompt rather than assuming capture is instant/always-on) — [Gamepad Tester site, via search summary](https://gpadtester.net/?p=29883)
- Unity's own filed bug about capture not suppressing live input (see Q3) is itself a UX-approachability finding: if the capture UI doesn't swallow the input, a non-technical user sees confusing double-effects (their current CATIA command fires *and* the new binding dialog reacts), which is exactly the kind of leaky abstraction that breaks trust in a remapping tool — [Unity Issue Tracker](https://issuetracker.unity3d.com/issues/input-system-interactive-binding-does-not-fully-suppress-controller-inputs-when-pressing-action-button)

### Inferences
- A visual controller diagram with clickable zones (implied but not explicitly documented as a named pattern in any single source retrieved) is the natural generalization of the capture-then-confirm pattern documented for Xbox/SteelSeries: click a DS4 zone on a diagram → enter "listening" state → press the physical button/stick/trigger → show the captured input name → let the user pick/search the target action → confirm. This matches every documented capture flow's shape even though no single source names "visual diagram" explicitly as the UI; it is the most direct way to disambiguate "which physical input" for a controller with as many input types as the DS4 (buttons, D-pad, 2 sticks, 2 analog triggers, touchpad position/click/swipe, gyro/tilt, L3/R3 clicks, PS/Share/Options/touchpad-click) — simply listing 20+ named inputs in a dropdown is far more error-prone for non-technical users than clicking a zone on a picture and having the app read back "you pressed: L2 (analog)".
- Given the AntiMicroX precedent (own users avoid hand-editing their own native format) and the reWASD guardrail design (un-mapped-in-layer falls back safely to Main), the "advanced/raw config" mode for this tool should be explicitly scoped to: (a) bulk editing/scripting many bindings at once, (b) sharing/importing profiles as files, and (c) defining things the visual UI intentionally doesn't expose (e.g., custom curve math for analog response, or COM-command target actions that need free-text CATIA command identifiers) — not as an alternate path for ordinary single-binding assignment, which the capture-then-confirm flow should always handle.
- Reserved/protected-input handling (the itch.io "don't let Backspace get bound over" lesson) maps directly onto this tool's own UI needs: the application's own hotkeys for opening its config window, pausing/disabling the controller mapping (a panic/safety switch), and switching profiles manually should be excluded from the capturable-input set, or at minimum require an explicit override confirmation, precisely because a DS4 has few enough controls that users may want to remap "everything," including the inputs the tool itself might want to reserve (e.g., PS button, or holding Share+Options together).
- Searchable/filterable target-action lists are implied as necessary rather than confirmed from a specific source: because this tool's target actions span three heterogeneous categories (keyboard shortcuts, mouse movement/clicks, and direct CATIA/COM commands), a flat dropdown is unlikely to scale; grouping by category with a search box is the standard mitigation pattern in UI design generally, though no input-remapping-specific source in this research confirmed this as a documented pattern — treat it as a design inference, not a cited finding.

### Gaps
- No source specifically addressed import/export/sharing of profiles as a discrete UX flow (e.g., "Export Profile," file picker, drag-and-drop a `.profile` file onto the app) in any of the surveyed tools' documentation; AntiMicroX's community-profile GitHub repo demonstrates that *file-based sharing* is the de facto standard (profiles are literally shared as files in a public repo organized by game name), but no source described the *in-app* import/export UI itself.
- No UX/HCI academic or practitioner article specifically about keybinding/controller-remapping interface design (as suggested in the task's source list) was retrieved in this session; all approachability findings above are inferred from vendor docs, bug reports, and developer forum posts rather than a dedicated UX literature source. A follow-up search specifically for HCI papers/articles on this topic (e.g. via Game UX literature, Nielsen Norman Group, or GDC talks on control-remapping UX) would strengthen this section.
- Drag-and-drop specifically as an action-assignment interaction pattern (named explicitly in the task's key questions) was not confirmed as implemented in any surveyed tool from the sources retrieved; this should be treated as a design option without found precedent rather than a validated pattern.

## What libraries/frameworks are recommended for building this configuration UI quickly on Windows, given it runs as a tray/background utility alongside CATIA V5?

### Takeaway
For a Windows-only tray-resident configuration tool, the realistic choices are a Python/PySide6 (Qt) app — which bundles a cross-platform tray API and a full widget toolkit in one dependency — or a .NET/WPF app, which has no built-in tray support and needs a third-party control such as H.NotifyIcon; a pure-Python lightweight alternative (pystray) exists for minimal tray-icon-only needs but lacks a full GUI toolkit for the config editor itself.

### Cited Findings
- Qt (and therefore PySide6) ships a built-in, documented cross-platform tray API: "Qt provides a simple interface for building cross-platform system tray... (Windows) or menu bar (MacOS) apps," via `QSystemTrayIcon` — [Qt for Python QSystemTrayIcon docs](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QSystemTrayIcon.html)
- Practical Qt/PySide6 tray gotchas documented by a PySide6 tutorial site: the Windows tray icon render size is 16x16 pixels; "Windows 10 and 11 sometimes hide system tray icons automatically" (an OS-level discoverability issue the app UI should account for, e.g. by prompting the user to pin the icon); and background-persistent apps need `app.setQuitOnLastWindowClosed(False)` so the process keeps running (and the tray icon keeps working) after the main config window is closed — [PythonGUIs system tray troubleshooting FAQ](https://www.pythonguis.com/faq/system-tray-examples-not-showing-up-on-windows-10/), [PySide6 System Tray tutorial](https://www.pythonguis.com/tutorials/pyside6-system-tray-mac-menu-bar-applications/)
- WPF has **no built-in tray-icon control**; the documented community solution is a third-party library such as **H.NotifyIcon**, described as "not just rely[ing] on the Windows Forms NotifyIcon component, but is a purely independent control" supporting notifications, context menus, `ICommand` binding, and an "efficiency mode for background operation," targeting ".Net 6 WPF/WinUI/Uno.Skia.WPF/Console" — [H.NotifyIcon GitHub](https://www.Github.com/HavenDV/H.NotifyIcon)
- A lightweight, GUI-toolkit-agnostic Python alternative exists for tray-icon-only needs: **pystray**, which exposes a unified `Icon`/`Menu`/`MenuItem` API across platforms, with the Windows-specific guidance to run the icon's blocking `run()` loop on a background thread so it doesn't block the rest of the app — [pystray docs, via search summary](https://docsearch.algolia.com/mcp/docs/repo/moses-palmer/pystray)

### Inferences
- For this specific project — a config UI with a controller diagram, live-capture flow, profile editor, and import/export, that must also run persistently in the background detecting CATIA's active workbench via COM — **PySide6 is the stronger fit** of the two main options: it supplies the full widget toolkit *and* the tray integration from one dependency (avoiding WPF's need for a separate third-party tray library), and Python's COM automation story (via `pywin32`/`comtypes`, not directly covered in this research pass but standard/well-known tooling for driving CATIA's VBA-equivalent COM interface, matching the `pycatia` project found during this research) is mature and widely used for exactly this kind of CATIA-automation task. WPF/.NET remains a reasonable alternative if the team prefers native Windows look-and-feel and C#/.NET tooling, but it requires explicitly adding H.NotifyIcon (or an equivalent) for tray support, which PySide6 provides natively.
- Given the task explicitly frames this as "running alongside/behind CATIA V5 as a tray/background utility," `setQuitOnLastWindowClosed(False)`-equivalent behavior (i.e., closing the config window should minimize to tray, not exit the process, since the background input-mapping/profile-switching engine must keep running) is a hard functional requirement regardless of framework choice, not just a nice-to-have — this is directly confirmed as a real implementation detail by the Qt tutorial source above and should be treated as a load-bearing requirement for either framework choice.
- A hybrid architecture (lightweight native tray via pystray or a minimal win32 tray icon, with the full config UI implemented as a local web server + default-browser or embedded-webview window, as the task's prompt also floated) was not evaluated by any source found in this research; no comparative data on this option versus PySide6/WPF was retrieved, so it remains an untested alternative rather than a validated recommendation either way.

### Gaps
- No direct, dated (2024–2026) head-to-head comparison article of PySide6/Qt vs. WPF vs. Electron-style web-shell for a Windows background utility was found; the comparison above is synthesized from each framework's own documentation/tutorials rather than a single authoritative comparative source.
- No source specifically addressed low-level DualShock4 input capture on Windows (e.g., via `hidapi`, `pyjoystick`, DirectInput/XInput wrappers, or a vendor SDK) — this research pass focused on the config-UI/schema/UX layer per the assigned scope, and DS4-specific Windows input-capture libraries were out of scope for this pass; this would need separate research if not already covered by another researcher on this effort.
- No source addressed packaging/distribution (e.g., PyInstaller for a PySide6 app vs. a WPF app's native `.exe`/MSIX) for this kind of persistent Windows utility; also likely out of this research pass's scope but worth flagging as unaddressed.
