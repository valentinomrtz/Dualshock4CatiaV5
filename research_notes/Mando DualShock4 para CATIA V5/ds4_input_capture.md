# Capturing Full DualShock 4 Input on Windows (Drivers/Libraries Comparison)

## Question 1: For each option — open source status, license, maintenance state, target language/platform, and library vs. standalone-app usability

### Takeaway
Almost everything in this space is open source, but maturity and maintenance are fragmented: the two "pillar" low-level drivers (ViGEmBus, the original DS4Windows) were both archived/discontinued in 2023–2024 over a trademark dispute and lack of maintainer time, leaving community forks of uncertain long-term status; hidapi and SDL2 remain the most solidly maintained cross-platform options; the Python DS4-specific ecosystem is thin (pydualsense targets the DualSense/PS5, not the DS4) and DS4-specific Python tooling (pyPS4Controller, ds4-tools) is Linux-oriented, low-activity, or explicitly experimental.

### Cited Findings
- **DS4Windows (original, Ryochan7 fork):** Open source, licensed under GPLv3 (source license was changed to GPLv3 as of the 3.3.3 release notes; COPYING file added) — [Ryochan7/DS4Windows releases](https://www.github.com/Ryochan7/DS4Windows/releases). The repository was **archived (read-only) by the owner on Jan 1, 2024**, with 3.3.3 marked as an **EOL release** — [search summary citing Ryochan7/DS4Windows repo metadata](https://awesome.ecosyste.ms/api/v1/projects/github.com%2FRyochan7%2FDS4Windows). It is a C#/.NET WPF **standalone end-user application** (system-tray GUI + background mapping service), not designed as an embeddable library.
- **DS4Windows forks:** `ds4windowsapp/DS4Windows` describes itself in its README as "the official continuation" and states it is licensed under **GPLv3**, though a third-party metadata aggregator (ecosyste.ms) separately tags the same repo "mit" — a direct conflict that could not be resolned from search snippets alone; the README's explicit GPLv3 statement should be treated as authoritative — [ds4windowsapp/DS4Windows](https://github.com/ds4windowsapp/DS4Windows). Requirements listed: Windows 10+, .NET 8.0 Desktop Runtime, VC++ 2015-2022 Redistributable. A second fork, `schmaldeo/DS4Windows`, reached v3.9.2/3.9.3-beta but **was itself archived by its owner on Mar 5, 2026** — [search result on schmaldeo/DS4Windows releases](https://www.github.com/Ryochan7/DS4Windows/releases). A commercial comparison blog (reWASD) states a fork by "hbashton" is "more actively developed" than ds4windowsapp, but this could not be independently verified in this research pass — [reWASD vs DS4Windows blog](https://www.rewasd.com/blog/post/rewasd-vs-ds4windows-which-one-should-you-choose).
- **ViGEmBus (Nefarius):** BSD-3-Clause licensed virtual-controller-emulation kernel driver — [ViGEm/HidGuardian README via search](https://github.com/ViGEm/HidGuardian). The official `nefarius/ViGEmBus` repository was **archived by the owner on Nov 2, 2023** due to a **trademark dispute** with a company called "ViGEM GmbH" discovered in May 2023; the project's own End-of-Life notice states "the ViGEmBus (and client libraries) project will no longer receive any updates and has been archived/retired" — [docs.nefarius.at End-of-Life notice](https://docs.nefarius.at/projects/ViGEm/End-of-Life/). It targets Windows 10/11 (x86, amd64, ARM64) from v1.17+. It is a **kernel-mode driver + C/C++/.NET client SDK**, i.e., it is consumed as a library/SDK embedded into other applications (this is exactly how DS4Windows itself uses it to emit a virtual Xbox 360/DualShock 4 controller) — [nefarius/ViGEmBus releases](https://github.com/nefarius/ViGEmBus/releases/tag/v1.21.442.0).
- **HidHide (Nefarius):** Kernel-mode HID filter driver, successor to the earlier "HidGuardian" research project (itself a successor to a proof-of-concept called "HideDS4") — [search summary of nefarius/HidHide & HidGuardian](https://github.com/nefarius/HidGuardian). Requires Windows 10+ and KMDF 1.13+; ships with a GUI configuration utility. Added a watchdog service in v1.4.181 to recover from configs broken by Windows Update. License info was inconsistent across NuGet listings seen (2.4.1 vs 3.4.0 version numbers appeared, and a note mentioned the ViGEm update-server URL being replaced "to mitigate ViGEm infrastructure EOL") — version/license should be re-verified directly on the GitHub releases page since results conflicted — [nefarius/HidHide](https://github.com/nefarius/HidHide). Unlike ViGEmBus, HidHide itself is still under the Nefarius org (not reported as archived in these results), so it appears to be the more durably maintained of the two Nefarius drivers, but this is an inference, not a directly confirmed "actively maintained in 2025/2026" statement.
- **SDL2 (SDL_GameController / SDL_Joystick, HIDAPI DS4 driver):** zlib-licensed, C library, cross-platform (Windows/Linux/macOS/consoles), maintained by the libsdl.org project — long-lived, high-activity upstream (not directly re-confirmed with a fresh commit date in this pass, but the SDL3-vs-SDL2 hint documentation being actively updated — e.g., `SDL_HINT_JOYSTICK_HIDAPI_PS4` documented as "available since SDL 3.2.0" for SDL3 — indicates ongoing development on the successor branch) — [wiki.libsdl.org SDL_HINT_JOYSTICK_HIDAPI_PS4](https://wiki.libsdl.org/SDL2/SDL_HINT_JOYSTICK_HIDAPI_PS4). SDL is a **library** meant to be embedded in applications/games (C API, with bindings for many languages), not a standalone end-user app.
- **hidapi (libusb/hidapi, formerly signal11/hidapi):** C library for raw HID access, cross-platform (Windows/Linux/macOS), triple-licensed — "HIDAPI may be used by one of three licenses as outlined in LICENSE.txt": **BSD-3-Clause, GPL-3.0, or the original permissive HIDAPI license** — [raw.githubusercontent.com libusb/hidapi README](https://raw.githubusercontent.com/libusb/hidapi/master/README.md). Latest observed release tag referenced was **0.15.0** (dated ~2025-07-08 per an Alpine package index) — [packages.ecosyste.ms Alpine hidapi listing](https://packages.ecosyste.ms/api/v1/registries/alpine-edge/packages/hidapi). An OpenSSF Scorecard snapshot gave it a "Maintained" score citing recent commit/issue activity within a 90-day window, though the snapshot's exact date wasn't confirmed — treat as directionally positive but not a precise maintenance date — [OpenSSF Scorecard via search summary]. It is a **library** (designed to be embedded), used by SDL2 internally as its own HIDAPI backend.
- **HidSharp (.NET, originally by James F. Bellinger, now under IntergatedCircuits org):** Apache-2.0 licensed per the NuGet page and developer's own page (one aggregator listed license as "other", so the LICENSE file should be checked directly to be certain) — [nuget.org HidSharp 2.1.0](https://www-0.nuget.org/packages/HidSharp/2.1.0). Latest NuGet version seen: **2.6.4**, with a 2.6.2 changelog entry dated **May 27, 2025**, adding a `HidSharpLibrary.ManualShutdown()` API — [nuget.org HidSharp](https://www.nuget.org/packages/HidSharp/). An ecosyste.ms snapshot showed the GitHub repo's last push around **September 2024** with 17 open issues — [awesome.ecosyste.ms IntergatedCircuits/HidSharp](https://awesome.ecosyste.ms/projects/github.com%2FIntergatedCircuits%2FHidSharp). It is a **C#/.NET library**, directly embeddable (no IPC/service needed), making it a strong fit for a custom C#/.NET application that wants raw DS4 HID access without a third-party driver.
- **HidApi.Net (badcel) / usb HID wrapper alternatives:** A newer C# binding of the native hidapi library was found (`badcel/HidApi.Net`, NuGet `hidapi.net` v1.2.0) as an alternative to HidSharp for .NET devs who want to reuse the native hidapi backend rather than HidSharp's own implementation — [github.com/badcel/HidApi.Net](https://github.com/badcel/HidApi.Net). Maintenance/license details were not independently verified in this pass — **gap**.
- **pydualsense (flok/pydualsense):** Explicitly a library for Sony's **DualSense (PS5)** controller, not the DualShock 4 — "use your DualSense (PS5) controller with python" — [pypi.org pydualsense](https://pypi.org/project/pydualsense). It is **not applicable to the DS4** as initially assumed in the task's suggested-sources list; this is an important correction. (It does use the `hid` Python package under the hood and implements report parsing/feature control, so architecturally it's a good reference for how one would build an equivalent DS4 library, but it will not work with a DS4 controller.)
- **pyPS4Controller (ArturSpirin/pyPS4Controller):** A lightweight, dependency-free Python module providing event hooks for DS4 input, but explicitly designed around **Linux** input paths — it hooks via Bluetooth and reads from `/dev/input/js0`, a Linux joystick device node that does not exist on Windows — [pypi.org pyPS4Controller description via search](https://pypi.org/project/pyPS4Controller/1.1.6). Reported community stats: ~134 stars / 33 forks on one aggregator — [relatedrepos.com ArturSpirin/pyPS4Controller](https://relatedrepos.com/gh/ArturSpirin/pyPS4Controller). **No Windows support was found**; this library is not a viable option for a Windows application without a Linux-compatibility shim (and even then it only exposes buttons/sticks via the Linux joystick API, not full touchpad/gyro — gap, see Question 2).
- **ds4-tools (dualshock-tools/ds4-tools):** A separate, explicitly experimental set of "Python scripts I use to play and reverse-engineer the DualShock 4 controller"; the author warns the scripts are risky and "could stop working the controller," and that it won't detect the DS4 "until you change default driver to the libusb one" — i.e., it requires replacing Windows' default USB driver (e.g., via Zadig/WinUSB), which is intrusive — [github.com/dualshock-tools/ds4-tools via search summary](https://github.com/dualshock-tools/ds4-tools). This confirms reverse-engineering activity exists but is not a production-ready library.
- **DirectInput vs XInput (native Windows):** No single library page covers this, but Microsoft's own XInput documentation states XInput supports "up to four unique controllers... at a time" and is the simplified, Xbox-controller-shaped API — [learn.microsoft.com Getting Started with XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput). XInput and DirectInput are both native Win32 APIs (C/C++, with COM for DirectInput), bundled in Windows — not separate open-source projects, hence no license/maintenance question applies; they are OS-level libraries any Windows app can call directly.

### Inferences
- The overall ecosystem health signal is: **driver/bus layer (ViGEmBus) = discontinued**, **flagship GUI app (DS4Windows) = discontinued, forked, fork status unclear**, **HidHide = Nefarius-maintained, status less clear from search alone**, **hidapi = actively maintained upstream**, **SDL2 = actively maintained (and its successor SDL3 clearly is)**, **HidSharp = maintained but with a slow pace (~17 open issues, infrequent pushes)**. For a *new* custom application in 2026, depending on an abandoned/archived driver (ViGEmBus, original DS4Windows) is a maintenance risk; a from-scratch raw-HID approach via hidapi or HidSharp avoids that dependency entirely.
- Because pydualsense targets DualSense and pyPS4Controller targets Linux, **there is no actively-maintained, Windows-capable, DS4-specific Python library with full feature support** identified in this research. A custom Windows/Python DS4 integration would most likely need to be built directly on top of the general-purpose `hidapi` Python bindings (or `hid`/`hidapi` PyPI package) using the raw report format (see Question 4), rather than reusing an existing DS4-specific package.

### Gaps
- Could not directly verify current commit/release dates for `nefarius/HidHide` (GitHub release page access was not attempted via gh CLI in this pass) — recommend verifying directly before final write-up.
- Could not confirm whether any ViGEmBus-compatible successor/continuation project (community fork) exists and is actively maintained in 2025–2026; the research only confirmed the original project's archival and the trademark-dispute rationale.
- `badcel/HidApi.Net` license/maintenance activity not verified.
- Exact current activity level (last commit date) of `ds4windowsapp/DS4Windows` fork not confirmed from search snippets.

## Question 2: Which tools expose the DS4 touchpad, gyro/accelerometer, light bar, and rumble — versus only a generic XInput-style gamepad abstraction?

### Takeaway
XInput (and anything that emulates XInput, including DS4Windows' virtual-controller output and ViGEmBus's x360 target) is button/stick/trigger-only and structurally cannot carry touchpad, gyro, or light-bar data — those are DS4-specific HID features with no XInput equivalent. Full feature access requires staying at the **native DS4 HID report level**, which is what DS4Windows does internally (to then re-map into XInput or DirectInput for other apps) and what SDL2's HIDAPI-based DS4 driver and raw hidapi/HidSharp access also do.

### Cited Findings
- Microsoft's XInput is fixed to the Xbox-controller feature set (buttons, two sticks, two triggers, one simple vibration pair) — this is implicit in XInput's own documentation describing "up to four unique controllers" with the standard XInput state structure — [learn.microsoft.com XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput); it has no fields for touchpad coordinates, gyro/accel, or RGB light bar — this is a structural fact about the XInput API surface, not something any of the search results needed to state explicitly, but it is corroborated by every tool in this list that treats "touchpad/gyro/lightbar" as a *separate, DS4-native* feature set requiring HID-level or vendor-specific access (see below).
- **DS4Windows** itself works by reading the DS4's **native/raw HID reports** (including touchpad and motion data) and internally remapping to either an emulated Xbox 360 controller (via ViGEmBus, XInput-compatible) or DirectInput; i.e., DS4Windows *does* parse the full native report, but the **output** most other applications consume from it (XInput) strips touchpad/gyro/lightbar down to nothing. Only DS4Windows-aware or DS4Windows-plugin-aware applications get the extra data back out. (Inferred from DS4Windows' documented purpose as "a gamepad input mapper and virtual emulator for PS4 and PS5 controllers on Windows" plus the existence of a "Hide DS4 Controller / Exclusive Mode" feature specifically to prevent the raw HID device from double-reporting — [Ryochan7/DS4Windows wiki: Exclusive Mode](https://github.com/Ryochan7/DS4Windows/wiki/Exclusive-Mode-(Hide-DS4-Controller-config-option)-tips-and-issues).)
- **ViGEmBus** is explicitly a **virtual-controller emulation** driver — "emulates well-known USB game controllers" (Xbox 360/XInput and DualShock 4 targets) — [nefarius/ViGEmBus releases](https://github.com/nefarius/ViGEmBus/releases/tag/v1.21.442.0). As an *output*-side driver, it is used to **create** a virtual gamepad that other apps see via XInput/DirectInput; it does not itself read the physical DS4's touchpad/gyro — that parsing has to happen in the client application (e.g. DS4Windows) before ViGEmBus is fed simplified button/axis data.
- **HidHide** only hides/filters HID devices from other applications' enumeration; it has no role in reading or exposing touchpad/gyro/lightbar data — [nefarius/HidHide via search summary](https://github.com/nefarius/HidHide).
- **SDL2** does expose the extended DS4 features, but through **separate, DS4/HIDAPI-specific APIs**, not through the generic `SDL_GameController` button/axis abstraction: a Godot engine issue explicitly states the touchpad field is **missing from `SDL_GameControllerDB`** mapping strings, meaning touchpad/gyro data is not reachable via the standard controller-mapping button/axis model — [github.com/godotengine/godot issue #55448 via search summary](https://github.com/godotengine/godot/issues/55448). Instead: (a) motion data (gyro/accel) is accessed via `SDL_GameControllerSetSensorEnabled()` + `SDL_GameControllerGetSensorData()` — confirmed by a libsdl.org forum user who enabled gyro this way — [discourse.libsdl.org DualShock 4 gyro thread](https://discourse.libsdl.org/t/dualshock-4-gyro-recognized-by-evdev-but-not-sdl/28561); (b) touchpad access uses separate touchpad-specific calls (a libgdx/Jamepad issue describes touchpad functions as containing "Touch"/"Touchpad" in their names, separate from motion "Sensor" functions, and notes a touchpad call failing "when the touchpad wasn't initialized in the HIDAPI driver" — implying SDL's HIDAPI-based DS4 driver specifically is the one that must be active) — [github.com/libgdx/Jamepad issue #21](https://github.com/libgdx/Jamepad/issues/21). Rumble and light-bar color are exposed through SDL's rumble/LED API calls tied to the HIDAPI PS4 driver, governed by hints such as `SDL_HINT_JOYSTICK_HIDAPI_PS4` and `SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE` — [wiki.libsdl.org SDL_HINT_JOYSTICK_HIDAPI_PS4](https://wiki.libsdl.org/SDL2/SDL_HINT_JOYSTICK_HIDAPI_PS4) / [SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE](https://wiki.libsdl.org/SDL2/SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE). Net: SDL2 **can** expose all the requested features, but a developer must use its HIDAPI/sensor/touch-specific function families, not the plain `SDL_GameController` button/axis API, and must ensure SDL's HIDAPI PS4 driver path is active (not the plain DirectInput/XInput joystick backend).
- **hidapi** and **HidSharp** expose the DS4 only as a **raw HID device** — they hand the application the exact bytes of each input report and let the application send raw output reports. This means touchpad, gyro, light bar, and rumble are all available, but **only if the application itself parses/constructs the DS4's native report layout** (see Question 4) — there is no built-in DS4-aware abstraction in either library; they are general-purpose HID libraries. (Directly supported by both libraries' stated purpose as generic cross-platform "USB HID API" wrappers — [raw.githubusercontent.com libusb/hidapi README](https://raw.githubusercontent.com/libusb/hidapi/master/README.md); [nuget.org HidSharp](https://www.nuget.org/packages/HidSharp/).)
- A Steam/Valve developer-facing reference independently confirms the DS4's touchpad is "Analog, 2 axes" and the gyro has "three axes," corroborating that these are real additional HID-reported axes beyond the standard gamepad set that any full-access approach must surface — [partner.steamgames.com PS4 Controller doc](https://partner.steamgames.com/doc/features/steam_controller/device/ps4_controller).

### Inferences
- There is a consistent two-tier pattern across every tool examined: a **"full/native" tier** (raw HID via hidapi/HidSharp, or SDL2's HIDAPI-specific sensor/touch calls) that can see touchpad + gyro + light bar + rumble + precise trigger pressure + battery, and an **"XInput-compatible" tier** (ViGEmBus output, DS4Windows's default virtual-controller output, plain DirectInput/XInput reads) that flattens everything down to the ~Xbox-controller feature set. For a custom application wanting full DS4 capability, the only reliable path is to read the DS4's native HID reports directly (via hidapi, HidSharp, or SDL2's HIDAPI backend with sensor/touch APIs) — not to go through any XInput-emulation layer.
- Because DS4Windows and ViGEmBus are oriented around *producing* an XInput-compatible virtual device for games that only understand XInput, they are the **wrong tool** for a custom application whose goal is to *consume* the full DS4 feature set (touchpad, gyro, light bar) — they solve the opposite problem. The right building blocks for the stated objective are hidapi/HidSharp (raw access) or SDL2 (if already using SDL for other reasons), reading/writing the native DS4 report structure directly.

### Gaps
- No source directly confirms whether DS4Windows (or its forks) expose a secondary/companion API (e.g., a named pipe, shared memory, or OSC feed as hinted by the existence of a "DS4Windows-with-OSC" fork — [github.com/GreySole/DS4Windows-with-OSC](https://github.com/GreySole/DS4Windows-with-OSC)) that a third-party app could tap for touchpad/gyro without reimplementing raw HID parsing itself. This fork's existence suggests some DS4Windows forks *can* re-expose extended data (via OSC messages) but this was not independently confirmed in detail.

## Question 3: USB vs. Bluetooth — differences in available features/report formats, and known Windows Bluetooth-HID reliability issues

### Takeaway
The DS4 supports an "extended" HID report (ID `0x11`) carrying touchpad + gyro/accel data on both USB and Bluetooth, but on **Bluetooth the controller boots into a basic, extended-feature-free mode and must be explicitly switched into extended mode via a feature report** — Linux does this automatically in its kernel driver, while **Windows does not do this automatically for generic HID consumers**, which is a well-documented source of "no gyro/touchpad over Bluetooth" problems unless the consuming application (DS4Windows, Steam, or a custom app) performs the mode switch itself.
### Cited Findings
- From a 2022 Wine developer mailing-list discussion analyzing DS4 Bluetooth behavior: "On Windows those use the basic reports (#1) by default and require getting calibration feature report (#5) to switch modes... The DS4 / DualSense in Bluetooth can be switched to a different mode in which they also report motion sensors, touchpad and other data." It further states Windows does **not** do this switch automatically the way Linux kernel drivers do, and that "when connected over bluetooth, DS4 controllers start sending input through report #17 [0x11] as soon as they receive a feature report #2, which the kernel sends anyway for calibration" (on Linux) — [list.winehq.org wine-devel thread, Jan 2022](https://list.winehq.org/archives/list/wine-devel@list.winehq.org/message/FST5UFTWHYMN2QHX325WQDVRHYPYB37A).
- The same thread cautions that "some games or applications are hard-coding the HID reports from the DS4... and expect them to match what Windows sends," meaning forcing the extended-report mode can be a visible behavior change for existing software — [list.winehq.org wine-devel thread](https://list.winehq.org/archives/list/wine-devel@list.winehq.org/message/FST5UFTWHYMN2QHX325WQDVRHYPYB37A).
- Per a Linux kernel driver patch-review comment (cross-platform-relevant as the canonical reference for the report layout): the DS4 **touchpad data offset shifts between USB and Bluetooth** — "offset 33 over USB and 35 over Bluetooth" — implying a **2-byte difference**, consistent with Bluetooth HID reports carrying a short additional header (commonly a leading report-ID/other framing byte over the BT HID transport) — [patchwork.kernel.org comment](https://patchwork.kernel.org/comment/19672761). A related summary states offsets are relative to the USB input report (0x01) and "Bluetooth (0x11) requires an additional +2" — [search synthesis of kernel patch, cross-referencing patchwork.kernel.org].
- Calibration/feature-report sizes also differ by transport: one summary of the kernel driver notes calibration feature report (0x05) sizes of **37 bytes for USB vs. 41 bytes for Bluetooth** — [search synthesis citing kernel driver/patchwork source].
- Real-world Windows reliability complaints exist but are largely informal: a Unity forum/issue-tracker report describes "DualShock4 controller returns random input values when connected via Bluetooth while Steam is running" — [Unity issue tracker](https://issuetracker-mig.prd.it.unity3d.com/issues/input-system-dualshock4-controller-returns-random-input-values-when-connected-via-bluetooth-while-steam-is-running); a Microsoft Q&A community thread on "PS4 controller not working" offers only generic advice (re-pair, clear Bluetooth cache, reinstall DS4Windows) with one user reporting Bluetooth works fine via a dongle — i.e., no authoritative/official Microsoft statement on a systemic Bluetooth-HID reliability problem was found, only anecdotal reports — [learn.microsoft.com Q&A thread](https://learn.microsoft.com/en-au/answers/questions/5648598/how-to-fix-ps4-controller-not-working).

### Inferences
- For a custom Windows application wanting full capability over Bluetooth, the application itself likely needs to replicate the "send feature report / enable extended report" handshake that Linux's kernel driver and tools like DS4Windows/Steam perform — simply opening the HID device on Windows and listening may yield only the **basic** (non-touchpad/non-gyro) report unless this handshake happens, or unless something else (another running tool) has already triggered it on that connection.
- Practically, **USB is the more reliable and simpler transport** for guaranteeing full-feature (touchpad+gyro) data from the first packet with no special enabling sequence, matching the general community guidance implied by multiple sources above suggesting wired connections "avoid the issue."

### Gaps
- No primary Microsoft documentation was found describing a built-in, systemic Windows Bluetooth-HID reliability defect (e.g., packet loss/throughput specific to BT HID vs BT LE or classic BT audio coexistence) — the reliability claims found were secondhand/anecdotal (forum reports), not confirmed root-caused sources. This should be treated as **plausible community folklore, not confirmed fact**, and flagged as such in the report.
- Exact byte-for-byte content of the Windows-side feature-report handshake (what bytes to send to force extended mode 0x11 over Windows Bluetooth HID) was not retrieved in this pass — the Wine thread describes the behavior but the exact command bytes were not captured in the search snippets; the psdevwiki DS4-BT page is likely the authoritative primary source for this handshake but could not be fetched (DNS blocked in this research environment — see Question 4 gaps).

## Question 4: Raw HID report format (report IDs, byte offsets) — is it documented, and could a custom app parse it directly without a third-party driver?

### Takeaway
Yes — the DS4's raw HID report layout is well documented in community reverse-engineering references (psdevwiki.com's DS4-USB/DS4-BT pages, a widely cited community gist, and cross-referenceable against the Linux kernel's `hid-playstation.c`/historical `hid-sony.c` source and Chromium's `dualshock4_controller.cc`), which collectively give enough information (report IDs, approximate byte offsets for sticks/buttons/triggers/touchpad/gyro/battery, and USB-vs-BT offset deltas) for a custom C#/.NET or Python app to parse the DS4 natively via hidapi/HidSharp — but this research pass could not directly fetch the two most load-bearing community wiki pages (psdevwiki, eleccelerator) due to this sandboxed environment's network allowlist blocking their domains, so the exact numeric offset table below is reconstructed from secondary citations of those sources and should be independently re-verified against psdevwiki.com and eleccelerator.com directly before implementation.

### Cited Findings
- **Primary community reference pages exist** but were **not directly fetchable in this research session**: `eleccelerator.com/wiki/index.php/DualShock_4` (DNS resolution blocked — "has to be allowed in the session's network settings") and `www.psdevwiki.com/ps4/DS4-USB` / presumably a parallel `DS4-BT` page (same DNS-block error). A Linux-kernel mailing-list thread explicitly references checking "the HID_INPUT_reports section on the DS4-BT page" on psdevwiki as the authoritative offset source — [lore.kernel.org thread referencing psdevwiki DS4-BT](https://lore.kernel.org/all/CANndSK=UHD0XJHuXBO-7PZ=LXQMwMS=6vJH255ZwBwVdUeaozg@mail.gmail.com/T/). **This is a known gap to flag for the final report: these two sites should be fetched directly (outside this sandboxed research tool, e.g. by the user or report writer) for the authoritative, complete byte-offset table.**
- **Report IDs confirmed:** USB input report ID **`0x01`**; Bluetooth extended input report ID **`0x11`**; a feature/calibration report **`0x05`** (for calibration data; sizes differ by transport — 37 bytes USB vs. 41 bytes Bluetooth per a synthesis of kernel driver code) — [list.winehq.org wine-devel thread](https://list.winehq.org/archives/list/wine-devel@list.winehq.org/message/FST5UFTWHYMN2QHX325WQDVRHYPYB37A); [patchwork.kernel.org comment](https://patchwork.kernel.org/comment/19672761).
- **Touchpad offset (USB):** multi-touch trackpad data begins at **byte offset 33** on USB, and **offset 35** on Bluetooth (i.e., **+2 bytes** for the Bluetooth framing/header vs. USB) — stated directly in a Linux kernel driver patch review comment: "The Dualshock 4 multi-touch trackpad data starts at offset 33 on USB and 35 on Bluetooth" — [patchwork.kernel.org comment](https://patchwork.kernel.org/comment/19672761). The same source notes the touch-count/contact-flag occupies the first byte of the touch block, with 12-bit X and Y coordinates packed across subsequent bytes using a shift-and-mask scheme (bit-packed, not byte-aligned) — exact bit-packing formula not fully captured in the search snippet; should be re-verified against `hid-playstation.c` or `hid-sony.c` source directly ([raw.githubusercontent.com/torvalds/linux .../hid-playstation.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/hid/hid-playstation.c) is the canonical current upstream Linux source for this, confirmed reachable in search results though full content was not pulled in this pass).
- **Battery offset:** an older/earlier version of the same kernel patch discussion mentions a prior battery offset of **30** (and touchpad offset of 32) before the patch's revision moved them to the 33/35 values above — implying the DS4 report layout has had at least one historical offset correction even within the Linux driver's own development history, which is a useful caution that "the" byte table is not perfectly static across all sources/firmware revisions and must be cross-checked carefully — [patchwork.kernel.org comment](https://patchwork.kernel.org/comment/19672761).
- **Gyroscope/accelerometer:** Chromium's own `dualshock4_controller.cc` device-abstraction header defines the motion fields as three sequential 16-bit fields for gyro — `uint16_t axis_gyro_pitch; uint16_t axis_gyro_yaw; uint16_t axis_gyro_roll;` — immediately followed by accelerometer fields of the same width, placed after timestamp and temperature fields in the packed struct — [chromium.googlesource.com dualshock4_controller.cc](https://chromium.googlesource.com/chromium/src.git/+/main/device/gamepad/dualshock4_controller.cc). This confirms gyro/accel are **signed 16-bit values**, matching the general community understanding that DS4 motion data is int16 per axis, but the **absolute byte offset** within the full 0x11 report was not resolved from the Chromium struct alone (it's positionally derivable by summing preceding field widths, but the exact total was not computed/verified against a primary numeric table in this pass — gap).
- **Cross-reference value of Linux source:** The current upstream Linux kernel driver is `hid-playstation.c` (which superseded the older `hid-sony.c` for PS4/PS5 controllers) and is directly reachable at `raw.githubusercontent.com/torvalds/linux/master/drivers/hid/hid-playstation.c` — this is the single most authoritative, actively maintained source for exact offsets/bit-masks, since it is production code shipped in the Linux kernel and kept in sync with real hardware behavior — [raw.githubusercontent.com hid-playstation.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/hid/hid-playstation.c). The research session surfaced this file's URL repeatedly across multiple kernel mirrors (AlmaLinux, Android KVM, OpenBMC, woboq code browser) confirming it's a stable, canonical reference, but the file's full ~2792 lines of content were not pulled into this pass — **recommend the report writer or implementer fetch this file directly for the ground-truth offset table**, since search snippets only gave fragments.
- **Output reports (rumble + light bar):** Not independently re-confirmed with exact byte positions in this pass (the eleccelerator/psdevwiki pages that document this were unreachable). It is widely known in the community (and indirectly corroborated by SDL2 exposing both "rumble" and light-bar/LED control as separate HIDAPI-driver features gated by hints like `SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE` — [wiki.libsdl.org SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE](https://wiki.libsdl.org/SDL2/SDL_HINT_JOYSTICK_HIDAPI_PS4_RUMBLE)) that the DS4 accepts an output report (commonly cited elsewhere in the community as report ID `0x05` over USB / `0x11` over Bluetooth output) containing rumble motor intensities and an RGB light-bar color, but the **precise byte layout was not verified against a primary source in this research pass** — flagged as a **gap** requiring direct retrieval of psdevwiki/eleccelerator or the Linux driver's output-report-construction code (e.g., `dualshock4_send_output_report` style functions in `hid-playstation.c`).
- **Feasibility conclusion (hidapi/HidSharp without a third-party driver):** Directly supported by the existence of multiple independent reimplementations that do exactly this — e.g., the `ds4-tools` Python scripts described as being used "to play and reverse-engineer the DualShock 4 controller" via raw USB access (after switching to the libusb driver) — [github.com/dualshock-tools/ds4-tools via search](https://github.com/dualshock-tools/ds4-tools) — and the `Alia5/VIIPER` Go library, which per its package path (`github.com/Alia5/VIIPER/device/dualshock4`) implements a dedicated DS4 device abstraction, further corroborating that the report format is reverse-engineered well enough to support independent, from-scratch implementations across multiple languages — [pkg.go.dev Alia5/VIIPER/device/dualshock4](https://pkg.go.dev/github.com/Alia5/VIIPER/device/dualshock4). (Its documentation site `alia5.github.io/VIIPER/...` likely has a clean offset table but was unreachable in this session — DNS blocked — another **gap** to re-fetch outside this sandbox.)

### Inferences
- A custom C#/.NET app using **HidSharp** (or **HidApi.Net**) or a Python app using the **hidapi**/`hid` PyPI bindings can absolutely read/write the DS4's native reports without ViGEmBus, DS4Windows, or any other third-party driver — multiple independent community projects already do exactly this (ds4-tools, VIIPER, SDL2's internal HIDAPI driver, the Linux/Chromium drivers used as reference). The dependency that *does* remain is on **documentation quality**: the implementer must obtain the exact offset table from psdevwiki.com/eleccelerator.com and/or read the Linux `hid-playstation.c` source line-by-line, since this research pass could only partially reconstruct it from secondary citations.
- Given the historical offset correction noted in the Linux kernel patch discussion (battery/touchpad offsets being revised from 30/32 to the current 33/35), **firmware/report-format stability across DS4 hardware revisions is not 100% guaranteed** — an implementer should defensively verify field values at runtime (e.g., sanity-check battery percentage range, touchpad coordinate range) rather than trusting a hardcoded offset table blindly.

### Gaps

## Question 5: Does Windows require special drivers, admin rights, or specific permissions for raw HID access to a DS4? Does the default Windows HID class driver block access?

### Takeaway
No admin/elevation requirement was found for basic raw-HID read/write access to a DS4 via `hidapi`/`HidD_*` Windows APIs — Windows' built-in HID class driver (`HidUsb.sys`/`hidclass.sys`) is multi-client by design (it maintains a per-device input-report ring buffer and is the mechanism hidapi/HidSharp both ride on top of), so no special third-party driver is needed to read raw reports; however, true **exclusive** (single-owner) access is a separate, harder problem on modern Windows, which is specifically why tools like HidHide exist as an alternative to relying on exclusive `CreateFile` locks.

### Cited Findings
- `HidD_SetFeature`'s own Microsoft documentation states "only user-mode applications can call HidD_SetFeature ... Kernel-mode drivers use a separate IOCTL instead" — confirming this is a user-mode-callable API requiring no special driver install for feature-report I/O, though this documents calling *context*, not privilege *level* — [Microsoft Learn HidD_SetFeature docs](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_setfeature) (no explicit elevation/admin requirement stated).
- No source found in this research stated that admin/elevated rights are needed merely to **open and read/write** a HID device's reports via `HidD_*` APIs or hidapi on Windows; the only admin requirement surfaced was for an unrelated helper script (`DS4Help`) that "needs admin rights to kill all the tasks" (a process-management need, unrelated to HID access itself) — [github.com/ZleMyzteX/DS4Help via search summary](https://github.com/ZleMyzteX/DS4Help).
- **Multi-client access is normal, not blocked:** Microsoft's HID concepts documentation describes the HID class driver as keeping "a ring buffer of input reports per top-level collection," adjustable via `HidD_SetNumInputBuffers` — a buffering/queueing model that is inherently designed to let the class driver mediate many reads rather than hand exclusive hardware ownership to one caller — [learn.microsoft.com Introduction to HID Concepts](https://learn.microsoft.com/nl-nl/windows-hardware/drivers/hid/introduction-to-hid-concepts). Real-world HID libraries (hidapi itself, and example projects like the Teensy "rawhid" code) open the device with sharing flags that **permit concurrent reads from other handles**, confirming non-exclusive, no-special-permission raw access is the normal/expected usage pattern — [sources.debian.org hidapi/windows/hid.c](https://sources.debian.org/src/hidapi/0.15.0-2/windows/hid.c).
- **Exclusive access is a separate, harder concern — and got harder on Windows 10 1607+:** DS4Windows' own wiki explains its "Hide DS4 Controller" exclusive-mode feature tries to `CreateFile` the device exclusively so other apps can't also see it, but "the attempt fails if any other process already holds a handle to the device" — [Ryochan7/DS4Windows wiki: Exclusive Mode](https://github.com/Ryochan7/DS4Windows/wiki/Exclusive-Mode-(Hide-DS4-Controller-config-option)-tips-and-issues). Separately, a cited Windows changelog note states: "As of update 1607, kernel32.dll CreateFile() using only the flags GENERIC_READ and GENERIC_WRITE and 0 for dwShareMode no longer allow exclusive (non shared) access to devices needed in some circumstances" — i.e., Windows itself **tightened/changed exclusive-access semantics starting with the Anniversary Update (1607)**, which is exactly why driver-level solutions (HidGuardian historically, HidHide currently) exist as the "recommended, trustworthy solution for preventing the double input issue," per multiple sources comparing the two approaches — [windowsreport.com Anniversary Update blocks Exclusive Mode](https://windowsreport.com/anniversary-update-exclusive-mode-game-controllers/).
- Net effect: the Windows **default HID class driver does not block** a custom app from opening and reading/writing a DS4's raw reports concurrently with other software (e.g., Windows' own Game Controllers panel, Steam, or DS4Windows can all be reading the same device at once) — the only thing a custom app *cannot* easily do without a filter driver like HidHide is **prevent other software from also seeing/reading the device** (useful to avoid double-input in games, but not required merely to capture full input data).

### Inferences
- For the stated objective (a custom application reading full DS4 input), **no admin rights and no third-party driver install are required** — a .NET app using HidSharp, or a Python app using the `hidapi`/`hid` package, should be able to enumerate the DS4 (VID `054C`, PID `05C4` for v1 DS4 / `09CC` for v2 DS4 — these PIDs are extremely well-known industry-standard identifiers, though not independently re-confirmed via a fetched source in this pass — minor gap) and read its reports without elevation.
- HidHide (or ViGEmBus+DS4Windows's exclusive mode) only becomes relevant if the custom application needs to **stop other software (e.g., games, Steam) from also seeing the raw DS4** — e.g., to prevent a game from reacting to both the raw DS4 and the custom app's own virtual-controller output simultaneously. For a pure "read full input for use inside one custom app" use case (as in the task's stated objective), this is likely unnecessary.

### Gaps
- Did not find a definitive, direct statement enumerating DS4 USB VID/PID values (054C:05C4, 054C:09CC) from a fetched primary source in this pass (this is extremely well-established industry knowledge but should be cited from psdevwiki or the Linux driver source directly in the final report rather than from training-data recall alone).
- Did not find explicit confirmation of whether Windows Update or OEM "game controller" drivers (vs. the generic HID class driver) ever auto-install a more restrictive driver for the DS4 specifically that would need to be rolled back to generic HID — gap, should be checked if real-world install issues are reported by the user's own hardware.

## Question 6: Can multiple DS4 controllers be distinguished/used simultaneously?

### Takeaway
At the raw-HID level, yes — each DS4 enumerates as its own distinct HID device with its own device path/handle, so hidapi/HidSharp/SDL2 can straightforwardly distinguish and read multiple controllers concurrently; the difficulty is specifically on the **XInput side**, where XInput's 4-slot model provides no device identifier at all, so correlating "XInput slot N" back to "physical DS4 X" is unreliable and slot assignment/order is not guaranteed to be stable or predictable.

### Cited Findings
- Microsoft's own XInput documentation caps support at "up to four unique controllers... plugged in at a time" — [learn.microsoft.com Getting Started with XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput).
- A developer-reported limitation: "the XInput API makes it impossible to tell which device sits behind an XInput controller index" — i.e., **XInput provides no VID/PID or serial-number correlation to its 4 slots** — [search synthesis of developer discussion, cross-referenced with discourse.libsdl.org "Supporting more than 4 XInput-capable devices on Windows [RFC]" thread](https://discourse.libsdl.org/t/supporting-more-than-4-xinput-capable-devices-on-windows-rfc/25666).
- An SDL community forum thread states plainly: "SDL can't tell which VID/PID matches up with which XInput slot, so if you have more than one controller attached you might see the wrong ones" — [discourse.libsdl.org SDL v2.0.7 joystick oddities](https://discourse.libsdl.org/t/sdl-v2-0-7-joystick-oddities/24025).
- DS4Windows' own documentation describes the hidden XInput slot model explicitly: "Upon connection, Xbox controllers are associated by Windows to hidden Xinput Slots that range from 1 to 4. After being associated they remain so until being unplugged" — confirming slot **persistence** per physical connection event, but not stable cross-session identity matching — [DS4Windows docs: xinput-slots-order](https://circumspector.github.io/DS4WDocs/troubleshooting/xinput-slots-order/).
- The DsHidMini SDK documentation (a related Nefarius project for DS3) explicitly warns: "Do not assume that the order of devices returned by SetupAPI or CM_Get_Device_Interface_List matches the slot order" — a direct caution against relying on HID enumeration order to infer XInput slot assignment — [DsHidMini Documentation](https://docsearch.algolia.com/mcp/docs/repo/nefarius/dshidmini).
- A **duplicate-device** side effect is well documented: when DS4Windows is running and converting the DS4 to XInput, the original raw DS4 can still be separately visible via DirectInput, causing "PS4 controller shows up twice" in some engines (Unity issue tracker) — [Unity issuetracker DS4 duplicate device](https://issuetracker-mig.prd.it.unity3d.com/issues/windows-gamepad-dualshock-added-twice-if-ds4windows-slash-ds4tools-is-installed-and-xinput-support-enabled); a GLFW community thread corroborates the same "Duplicate joysticks when using DS4Windows" symptom — [discourse.glfw.org Duplicate joysticks with DS4Windows](https://discourse.glfw.org/t/duplicate-joysticks-when-using-ds4windows/665).

### Inferences
- For a custom application built on **raw HID (hidapi/HidSharp)**, multi-controller support should be straightforward and reliable: each DS4 has a distinct Windows device path (and, per the DS4's own HID report data, likely an accessible unique identifier — e.g., a MAC address field is commonly reported in the DS4's extended report per general community knowledge, though this was not independently re-confirmed from a fetched primary source in this pass — gap); the HID layer itself is not where the "which controller is which" ambiguity lives.
- The ambiguity problem is **specific to the XInput abstraction layer** (and by extension, any tool whose *output* is XInput, such as ViGEmBus-emulated controllers or DS4Windows' default XInput output mode). Since the custom application in the stated objective wants **raw/full** DS4 data rather than XInput compatibility, this entire slot-ordering problem is avoidable by bypassing XInput altogether and reading each DS4 directly via its own HID device handle — reinforcing the Question 2/4 conclusion that raw HID access (not XInput, not ViGEmBus output) is the right architecture for this project.

### Gaps
- Did not independently verify (from a fetched primary source) whether the DS4's HID report or feature-report data includes a readable Bluetooth MAC address or other stable serial-like identifier that a custom app could use to persistently distinguish controller "A" from controller "B" across reconnects — this is commonly assumed in the community but was not directly confirmed via a source fetched in this session. Should be checked in `hid-playstation.c` (a `get_feature_report`/MAC-address-read function is typically present in Linux PS4 drivers) or psdevwiki once accessible.
- Did not find a definitive statement on whether more than 4 DS4s can be used simultaneously if staying entirely at the raw-HID level (bypassing XInput's 4-controller cap) — logically there should be no such cap outside of XInput/DirectInput legacy limits, but no source explicitly confirmed an upper bound (or absence of one) for raw HID DS4 enumeration on Windows.
