# CAD/3D Software Controller Integration — Precedents and Architecture Patterns

## How does 3Dconnexion's SpaceMouse integrate with CAD software, and does CATIA V5 have native support?

### Takeaway
3Dconnexion's integration is a **hybrid, two-layer model**: a persistent background driver (3DxWare) owns the physical device and exposes a vendor API/SDK, and individual CAD applications (including CATIA V5) each contain their own native plugin code written against that SDK to translate 6-DOF motion into camera navigation and to receive dynamic, context-sensitive button labels/commands from the app. CATIA V5 has long-standing native 3Dconnexion support (it is one of 3Dconnexion's officially listed/certified applications), but most real configuration happens in the 3DxWare driver UI rather than inside CATIA itself, and CATIA has had version-specific detection/compatibility bugs.

### Cited Findings
- 3Dconnexion publishes a dedicated "CATIA" / "3DEXPERIENCE CATIA" application support page listing supported navigation features — [CATIA and 3Dconnexion](https://3dconnexion.com/applications/dassault-systemes-catia-v5/); [3DEXPERIENCE CATIA Features](https://3dconnexion.com/us/applications/dassault-systemes-3dexperience-catia/learn-more/)
- A 3Dconnexion forum moderator advised that device/navigation settings should be made in the 3Dconnexion driver rather than in CATIA itself — [forum post](https://forum.3dconnexion.com/viewtopic.php?p=69654)
- A user found that changing navigation options in the driver's own menu changed which icons/toolbar buttons appeared inside CATIA, i.e., the driver and the app's UI are linked/synchronized — [forum post](https://forum.3dconnexion.com/viewtopic.php?p=77187)
- 3Dconnexion ships a documented procedure specifically for "How to change the SpaceMouse rotation point in CATIA, ENOVIA and DELMIA V5," confirming CATIA-family apps have dedicated, documented driver-side configuration — [3Dconnexion KB article](https://3dconnexion.com/dk/?p=5513)
- There is a known CATIA-specific bug: if the Windows environment variable `ADL_ODT_IN` is defined, the SpaceMouse fails to navigate in CATIA V5; the fix is to remove it and use `CATNoStartDocument` instead — [3Dconnexion KB: "No navigation with SpaceMouse in CATIA V5"](https://3dconnexion.com/uk/?p=5392)
- Users report CATIA sometimes misidentifies a newer SpaceMouse model as an older "SpacePilot PRO," which blocks button customization specific to the real device — [forum post](https://forum.3dconnexion.com/viewtopic.php?p=74345)
- A separate forum reply states CATIA's own in-app button customization options are more limited than what the driver itself exposes — [forum post](https://forum.3dconnexion.com/viewtopic.php?p=68709)
- A user reported lag/latency using the SpaceMouse in CATIA V5, with a suggested fix of adjusting CATIA's own mouse-related navigation settings and checking graphics driver configuration — [GrabCAD Q&A](https://print.grabcad.com/questions/does-somebody-use-a-space-mouse-3d-connexion-on-catia-v5-how-to-set-up-an-space-mouse-on-catia-v5)
- Autodesk's own blog on the Fusion 360 integration states Fusion 360 uses the latest 3Dconnexion SpaceMouse SDK v4.0 on Windows (vs. v3 on macOS), that "all commands [can be] mapped directly to 3Dconnexion buttons with complete customizability," and that **the driver provides raw navigation data while the host app (Fusion) calculates/applies the actual navigation** — i.e., the SDK is a data feed, and view-math/interpretation is the host application's own responsibility, not something 3Dconnexion controls externally — [Autodesk Fusion 360 blog](https://www.autodesk.com/products/fusion-360/blog/fusion-360-3dconnexion-spacemouse-integration/)
- Shapr3D's compatibility documentation lists exact tested 3DxWare driver build numbers (10.8.20 Windows, 10.8.4 macOS) as a hard runtime dependency for its integration, confirming 3DxWare is a versioned runtime component that host apps must track — [Shapr3D and 3Dconnexion](https://3dconnexion.com/applications/shapr3d)
- IntelliCAD's integration was built "in partnership with 3Dconnexion, using the freely available 3Dconnexion Software Development Kit (SDK)" — confirming a public/free SDK exists for third-party CAD vendors to build native support — [Digital Engineering 24/7](https://digitalengineering247.com/article/intellicad-technology-consortium-and-3dconnexion-form-integration-partnership)
- HiCAD's page states 3Dconnexion buttons "automatically detect the environment and provide the relevant commands," evidencing dynamic, context-aware command sets pushed from the app to the device (not static, hardwired button bindings) — [HiCAD and 3Dconnexion](https://3dconnexion.com/applications/isd-software-und-systeme-hicad/)
- 3Dconnexion runs a "Software Developer Program" offering SDKs for Windows/macOS, but marketing-level pages did not surface technical architecture detail (byte-level HID report formats, API object model) in this research pass — [Software Developer Program](https://3dconnexion.com/au/?p=3174)
- Developer forum threads show some third parties bypass the SDK entirely and talk to the device over **raw HID** instead (reading HID usage pages, including a vendor-specific page `ff00` seen on SpaceNavigator), with 3Dconnexion staff redirecting such questions to a dedicated API Support team — [forum thread on HID/SDK](https://forum.3dconnexion.com/viewtopic.php?p=125178); [forum thread on HID report format](https://forum.3dconnexion.com/viewtopic.php?p=81347)
- 3Dconnexion's SDK documentation explicitly recommends developers code support for "Virtual 3D Mouse Commands (V3DCMD)," a logical/virtual command abstraction layer above raw device I/O — [forum reference to SDK docs](https://forum.3dconnexion.com/viewtopic.php?p=70516)

### Inferences
- The overall pattern is: **3DxWare driver (background, persistent, owns the physical USB device + exposes SDK/COM-style API) → native per-application plugin (written by the CAD vendor against the 3Dconnexion SDK) → app-specific navigation logic**. The driver is not purely a dumb HID passthrough nor a full injector of synthetic mouse/keyboard events into the app; it is a true bidirectional SDK integration where the app pulls raw 6-DOF deltas and pushes back context (active command set, which buttons exist, labels).
- This architecture requires CATIA (and every other supported app) to ship native, app-specific integration code — it is not something a third party can bolt on externally without CATIA's own cooperation/API surface, which is a meaningfully different approach than input-injection or virtual-HID options available for a DualShock4 project.
- The CATIA-side bugs/limitations documented (SpacePilot PRO misdetection, `ADL_ODT_IN` conflicts, limited in-app customization vs. driver) suggest CATIA's native 3Dconnexion plugin is comparatively old/under-maintained relative to e.g. Fusion 360's integration, which is a useful data point: native official support still has real rough edges in CATIA specifically.

### Gaps
- Could not retrieve the exact technical architecture whitepaper for 3DxWare (e.g., whether it's a Windows service, named pipe/COM server, or shared memory API) — marketing and KB pages did not go into OS-level implementation detail, and the official SDK documentation itself was not directly fetchable in this research pass (3dconnexion.com was not reachable via direct fetch in this environment; only search-engine snippets were available).
- Could not confirm whether CATIA V5 specifically exposes a visible "3D Mouse"/"SpaceMouse" entry under Tools > Options (vs. all configuration happening in the external 3DxWare control panel) — forum evidence strongly suggests most settings live in the driver, with only some CATIA-side toolbar/button customization, but an authoritative CATIA V5 manual page naming the exact menu path was not found.

## Are there known open-source/hobbyist projects mapping a gamepad (or DIY controller) to CAD or general 3D navigation, and what architecture do they use?

### Takeaway
Gamepad-to-3D-navigation precedents exist but are scattered and mostly built around **mouse/keyboard emulation rather than deep native API integration**: Blender has a dedicated commercial add-on ("Gamepad Navigator") built for XInput controllers, a third-party plugin exists for Autodesk Navisworks using FPS-game-style controls, and several hobbyists have built DIY physical controllers (Arduino-based joysticks, magnet-based "space mice") that all ultimately emulate standard mouse/keyboard events to drive Fusion 360/SolidWorks rather than talking to any CAD-specific API. No native, first-party Autodesk or Dassault gamepad support was found.

### Cited Findings
- "Gamepad Navigator" is a paid Blender add-on, distributed on Blender Market/SuperHive, explicitly described as working with "any 'XInput' controller, such as Xbox controllers," for 3D-viewport navigation — [search result summary citing Blender Market listing](https://blendermarket.com/products/gamepad-navigator) (direct fetch of the docs page failed: `superhivemarket.com` was not reachable in this research environment)
- Buildfore built a custom Xbox controller plugin for Autodesk Navisworks, explicitly modeled on first-person-shooter game controls, and the listing notes it is supported only on Navisworks Manage and Simulate (not the free Navisworks Freedom viewer) — [Medium: "We built an Xbox Controller plugin for Navisworks"](https://medium.com/buildfore/we-built-an-xbox-controller-plugin-for-navisworks-f09dd03af3bf) (title/summary from search snippet only; direct fetch of medium.com failed in this environment, so internal architecture detail from that article could not be confirmed firsthand)
- Esri community members have separately discussed "3D navigation with Xbox controller" in the context of ArcGIS 3D scenes, indicating the gamepad-for-3D-navigation idea recurs across multiple 3D software ecosystems, not just CAD — [Esri Community discussion](https://community.esri.com/discussion/903726/3d-navigation-with-xbox-controller)
- On the Autodesk forums, a user explicitly asked how to "bind analog gamepad axis to movement commands" (pan/zoom/orbit) in Fusion 360; the top community reply said they personally "would never use a gamepad to model" in Fusion 360 but could see gamepad navigation (as opposed to modeling) as plausible — [Autodesk forum thread](https://forums.autodesk.com/t5/fusion-360-ideastation-archived/bind-analog-gamepad-axis-to-movement-commands/idc-p/7105146)
- A separate Autodesk support thread documents a regression where, after a Fusion 360 update, a connected game controller's joystick began panning the workspace vertically instead of zooming — direct evidence that at least some version of Fusion 360 had *some* built-in game-controller input handling (likely incidental, via generic joystick/game-controller OS APIs) that could regress across updates — [Autodesk forum: "using a controller to zoom is broken after update"](https://forums.autodesk.com/t5/fusion-support-forum/using-a-controller-to-zoom-is-broken-after-update/m-p/13294657)
- A hobbyist built a DIY joystick-based "Simple CAD Joystick" (Arduino Pro Micro) specifically to navigate 3D models, with build notes explicitly stating: in Fusion 360 you hold the middle mouse button to orbit, while SolidWorks orbits directly on middle-mouse-button-drag — implying the DIY controller's firmware/host script emulates **mouse button + movement**, tuned per-CAD-app convention, rather than calling any CAD API — [MakerWorld: "Simple CAD Joystick"](https://www.makerworld.com/en/models/2474475-simple-cad-joystick)
- Another hobbyist (Hackster.io) built a magnet-based DIY "space mouse" for Fusion 360 that explicitly works by "emulat[ing] the mouse and keyboard to execute the orbit and pan functions" — again, mouse/keyboard emulation, not an API hook — [Hackster.io: "DIY Space Mouse for Fusion 360 Using Magnets"](https://www.hackster.io/ocr_lab/diy-space-mouse-for-fusion-360-using-magnets-a1e480)
- Fusion 360 ships built-in alternate navigation presets (Fusion default / SolidWorks-style / Inventor-style) for mouse-button-to-pan/zoom/orbit mapping, which DIY and third-party tools deliberately target/mimic rather than inventing their own scheme — [Autodesk Fusion 360 blog on Pan/Zoom/Orbit preferences](https://www.autodesk.com/products/fusion-360/blog/de/quick-tip-pan-zoom-orbit-preferences/)
- General-purpose "Xpadder" (keyboard/mouse emulation from an Xbox 360-style controller) is suggested in search-result commentary as a ready-made fallback for gamepad-to-keystroke mapping in arbitrary Windows apps including CAD tools, though Xpadder's own site/architecture documentation could not be directly fetched in this pass — [search summary](https://www.filehorse.com/download-xpadder) and related listicle coverage

### Inferences
- Across every hobbyist/third-party example found (Blender add-on, Navisworks plugin, DIY Arduino joystick, DIY magnetic mouse), the **common architecture is "read the controller, then emulate standard mouse/keyboard events into the app"** — none of them call into a CAD vendor's internal navigation API, because such APIs are either undocumented, unavailable, or not worth the integration cost for a side tool. This strongly supports an input-emulation approach (vs. deep CATIA API hooking) for a DS4→CATIA V5 integration, consistent with how virtually every other non-native gamepad-to-CAD bridge has been built.
- The repeated convention of targeting "hold middle-mouse-button to orbit" / "drag with mouse to pan" suggests that for CATIA V5 as well, the most portable, version-resilient integration surface is standard middle-mouse-drag emulation (which CATIA V5's native navigation already understands) rather than keyboard shortcuts, which can differ by CATIA workbench/version.
- The "gamepad detected by Fusion 360 and broke after an update" report suggests Fusion 360 may read generic Windows joystick/XInput APIs directly for some navigation purposes, hinting that some mainstream CAD packages have at least rudimentary, undocumented native gamepad awareness — but this appears incidental/fragile rather than a deliberately supported feature, and nothing equivalent was found for CATIA V5.

### Gaps
- Could not directly fetch/verify the internal architecture of "Gamepad Navigator" for Blender (SDL2 vs. Blender's own `bpy` input handling, whether it uses NDOF emulation internally, deadzone/curve configuration) because `superhivemarket.com` could not be resolved in this research environment. Blender's native NDOF (3D-mouse) pipeline is well documented (see next section's findings on Blender NDOF), but the add-on's own gamepad-specific internals remain an open gap.
- Could not directly fetch the Buildfore Navisworks Medium article body (`medium.com` unreachable in this environment), so the plugin's actual input-reading/injection mechanism (native Navisworks API vs. SendInput) is inferred only from the listing's title/summary, not confirmed firsthand.
- No evidence was found of any gamepad-to-CATIA-V5-specific project (open-source or commercial) predating this one; this appears to be a genuinely underserved niche compared to Blender/Fusion 360/Navisworks.

## General-purpose Windows input-remapping tools (JoyToKey, AntiMicroX, reWASD, Steam Input) as architecture references/fallback layer

### Takeaway
These tools cluster into two architectural families: **(1) keyboard/mouse-event emulators** (JoyToKey, AntiMicroX, Xpadder) that run as a background process/daemon and call OS-level input-injection APIs, and **(2) virtual-controller emulators** (reWASD, Steam Input, and driver layers like vJoy/ViGEm that these and similar tools build on) that hide the physical pad and present a brand-new virtual HID/XInput/DirectInput device to the OS and target app. All of them are long-running background processes driven by switchable, user-edited profile files, and most support deadzones, output curves, macros, and some form of profile/mode switching that functions as "shift states," though exact feature depth (e.g., true chorded combos) varies and was not fully confirmed for every tool.

### Cited Findings
- **AntiMicroX**: reads gamepads via SDL2 (which on Linux uses evdev under the hood); a D-Bus service (`io.github.antimicrox`) exposes device description (SDL GUID, button/axis/hat counts) and lets external processes select the active "control set" programmatically; supports a background/daemon launch mode; maps gamepad buttons/axes to keyboard keys, mouse buttons, mouse movement, scripts/executables, and macros; supports multiple switchable "sets" per gamepad (effectively shift-layers), and an "auto profile" feature that switches profile based on the active foreground application window (not supported on Wayland) — [AntiMicroX README](https://raw.githubusercontent.com/AntiMicroX/antimicrox/master/README.md)
- AntiMicroX profile files are managed through a dedicated companion repository of shareable profiles, but the exact on-disk format (XML/INI/JSON) was not confirmed by the README fetch in this pass — [AntiMicroX README](https://raw.githubusercontent.com/AntiMicroX/antimicrox/master/README.md)
- **reWASD**: explicitly emulates virtual controllers — Xbox 360, DualShock 4, Xbox One, Switch Pro, and DualShock 3 — meaning it can take one physical pad's input and re-present it to Windows/games as a *different* virtual controller type; the official docs warn that if the physical gamepad is not hidden, its native input and the virtual mapped input can both reach the game and "cause unpredictable consequences," confirming a device-hiding/virtual-HID architecture rather than pure event injection — [reWASD virtual controller docs](https://help.rewasd.com/basic-functions/virtual-controller.html) (summarized via search snippet; direct fetch failed, host unreachable in this environment)
- reWASD organizes mappings into **Profiles → Configs**: a Profile represents a given game/app, and each Profile can hold multiple Configs (the actual button-layout mappings); profiles can be switched manually from the system tray, via hotkey, or auto-loaded per detected title — [reWASD blog: "How to Remap Any Controller on PC"](https://www.rewasd.com/blog/post/how-to-remap-any-controller-on-pc-complete-guide); summarized via search
- reWASD ships its own kernel-level virtual controller driver for the device emulation (per third-party installer-guide commentary), and some games are reported to detect/reject virtual inputs and disable mapping as a result — [search summary of reWASD coverage]
- **Steam Input** (Valve): defines "Action Sets" in a developer-authored in-game-actions (IGA)/VDF file; the running game calls the Steam API to tell Steam Input which Action Set is currently active (e.g., "menu" vs. "gameplay" controls), and "Action Set Layers" are optional partial overlays that can be stacked on top of an active Action Set to apply small contextual modifications — both are effectively a formal "layers/shift-state" system — [Steamworks docs: Steam Controller concepts](https://partner.steamgames.com/doc/features/steam_controller/concepts)
- Steam Input's VDF/IGA action-naming has a hard constraint: action string identifiers must be unique across the whole file, even across different Action Sets, or the lookup function silently resolves to only one — a documented pitfall for anyone designing similar named-action profile schemes — [Steamworks docs: IGA file reference](https://partner.steamgames.com/doc/features/steam_controller/iga_file)
- **JoyToKey**: is a long-running freeware background utility; converts controller input to keyboard-key and mouse-button/movement events; supports 16 switchable profiles; has a secondary "virtual joystick" layer — a button held to access a second bank of mappings, functionally a shift-state — letting one physical controller expose more logical mappings than it has physical buttons; recent versions improved analog-stick-to-mouse-cursor smoothing — [search summary of JoyToKey feature/changelog pages]; exact profile file format (XML vs. proprietary) could not be confirmed directly in this pass
- **DS4Windows** (directly relevant as a DualShock4-specific precedent): supports per-axis "anti-deadzone" (minimum output threshold once the stick clears its deadzone, configured in the profile's Axis Config/Readings tab); supports multiple selectable output curve shapes per stick — Linear, Enhanced Precision, Quadratic, Cubic, two ease-out variants, and a fully Custom Bezier curve drawn in a companion web tool; includes a "Special Actions" tab with a Record Macro feature bound to a trigger button, allowing recorded key-press sequences — [DS4Windows docs: Controller Deadzone](https://ds4-windows.com/?p=2670); [search summary of DS4Windows Maxzone/curve settings]
- A DS4Windows community bug report shows a real limitation relevant to chorded/simultaneous macros: when two macros are triggered at once, the longer-running macro gets cut short as soon as the shorter one finishes — a concrete pitfall to avoid when designing chord/combo timing logic — [PCSX2 forum: "DS4Windows J2K" thread](https://forums.pcsx2.net/Thread-DS4Windows-J2K?page=61)
- **vJoy** and **ViGEm** are the two most common underlying *virtual joystick/gamepad driver* building blocks used by higher-level remapping tools on Windows: vJoy is a driver letting software expecting a physical joystick receive input from non-joystick sources, offering a simple stable build (1 device, 8 axes, 32 buttons) and a more configurable 2.x branch (up to 16 virtual devices); ViGEm is a kernel-mode bus driver presenting virtual USB Xbox/DualShock-style controllers to Windows and games, BSD-3-Clause licensed, but the project is now explicitly **retired/end-of-life**, with Windows 10/11 (x86/amd64/ARM64) being the last supported scope — [vJoy overview](https://sourceforge.net/app/vjoy/); [ViGEmBus GitHub README](https://github.com/nefarius/ViGEmBus) (ViGEmBus retirement status per GitHub README notice)

### Inferences
- There are really only two architectural "shapes" among all of these tools: **emulate standard input (keyboard/mouse events)**, or **emulate a different/virtual controller device**. A DS4→CATIA bridge could follow either model: emulate mouse (middle-drag for orbit/pan, wheel for zoom, matching what CATIA V5 already natively understands via its own mouse-driven navigation) — this is the path every hobbyist CAD-gamepad project above actually took — or emulate a 3Dconnexion-style virtual "SpaceMouse" device if CATIA's native 3Dconnexion SDK plugin could be fooled into reading it (much higher effort, no precedent found of anyone doing this for an arbitrary gamepad).
- The "Profile → Config" / "Action Set → Action Set Layer" structure used by both reWASD and Steam Input is a validated, user-tested pattern worth imitating for a CATIA bridge: one top-level "Profile" selects context (e.g., "CATIA Part Design" vs. "CATIA Assembly Design" workbench), and layered/secondary mapping banks (shift-states, held-button combos) handle context-dependent commands without needing a new physical button per function.
- DS4Windows's curve/deadzone system (multiple named curve shapes plus a custom Bezier editor) is a strong direct reference since it already targets the exact same controller (DualShock4) and solves the identical problem of turning noisy analog stick/trigger data into controllable, non-jittery continuous output — this is likely the single closest existing precedent to reuse conceptually.

### Gaps
- Could not confirm JoyToKey's or Xpadder's exact on-disk profile file format (several listicle/aggregator sources were ambiguous or did not specify it); only Joystick Gremlin Ex was confirmed to use XML among the tools searched, so the DS4→CATIA project's own config-format choice (JSON/XML/INI) has no single "industry standard" to copy — all of these tools diverge.
- Could not directly fetch reWASD's and Steam Input's full technical docs pages in this environment (`help.rewasd.com` unreachable; Steamworks pages were search-summarized rather than fully fetched), so finer details of their deadzone-curve UI and exact combo/chord implementation are not independently confirmed beyond what the search snippets state.
- Steam Input's gyro-to-mouse remapping mechanics for non-Steam-native ("API") games specifically could not be confirmed — search results covered native Steam Input API action sets well, but gyro-specific configuration details for arbitrary games were inconclusive and partly contradictory in secondary sources.

## What common architecture pattern emerges, and what are the tradeoffs (background daemon vs. virtual device driver vs. API/SDK hooks vs. synthetic input injection)?

### Takeaway
Across every precedent found, four distinct patterns recur, and the real-world tools mostly combine two of them (a background daemon reads the controller continuously, which then either injects synthetic input or drives a virtual device): (a) **background daemon + OS-level synthetic input injection** (JoyToKey, AntiMicroX's keyboard/mouse output, DS4Windows's pointer/key emulation, all DIY CAD-joystick projects) is simplest and lowest-effort but is visible to anti-cheat/anti-injection detection and gives the target app zero awareness that input is continuous/analog versus discrete; (b) **background daemon + kernel-mode virtual HID/XInput device** (reWASD, ViGEm/vJoy-based tools) is harder to detect and lets the OS/app treat the input as a "real" peripheral, at the cost of needing a signed kernel driver, extra install complexity, and potential conflicts if the physical device isn't also hidden; (c) **direct API/SDK hooks into the target app** (3Dconnexion's native per-CAD-app plugins) give the richest, most correct continuous-navigation behavior and dynamic context-awareness, but require the target application's own vendor to have built and shipped that integration — not available to a third party targeting CATIA V5 with a DS4; (d) **raw SendInput-style synthetic injection at the OS level** is the easiest of all four to implement (no driver) but is explicitly the easiest for monitoring software to flag (e.g., via `LLKHF_INJECTED` flags), and is a strict subset of pattern (a).

### Cited Findings
- SendInput-generated input carries low-level hook flags (e.g. `LLKHF_INJECTED`) that make it readily identifiable as synthetic/non-physical by monitoring code, and reliance on SendInput alone "can lead to detection and rejection by anti-cheat systems" — [AutoPTT: Simulating hardware keyboard input on Windows](https://fooqux.com/article/1912)
- A virtual-mouse driver guide notes SendInput is "generally indistinguishable from a real USB mouse to user-mode code," but its limit is kernel-level anti-cheat/monitoring, which can still see the injection — [AI-Ming: Mouse Input Methods](https://fgilde.github.io/AI-Ming/features/mouse-input-methods/)
- Games using kernel-level anti-cheat (cited example: Valorant's Vanguard) have been reported not to recognize or accept high-level virtual HID input at all in some cases — [Apollo GitHub issue #1202](https://github.com/ClassicOldSong/Apollo/issues/1202)
- Virtual HID driver approaches "present as real HID devices, emitting input indistinguishable from physical user actions to applications," and are recommended to be WHQL-signed to avoid heuristic flags by kernel-level anti-cheat software — [attackshark.com: Anti-Cheat and Rapid Trigger blog](https://attackshark.com/blogs/knowledges/anti-cheat-rapid-trigger-hardware-detection-guide)
- Kernel-mode input-injection drivers can have real robustness limits: the `MouClassInputInjection` project's own README states it "was not tested against kernel mode anti-cheat software," and separately notes that monitoring software can use input hooks (`SetWindowsHookExA`, `WM_INPUT`) and detect malformed/anomalous input data as a sign of injection — [MouClassInputInjection GitHub](https://github.com/changeofpace/MouClassInputInjection)
- ViGEm (the most widely reused general-purpose virtual-gamepad kernel driver on Windows) is now explicitly retired/EOL per its own GitHub README, which is an important caveat for anyone planning to build on it today — [ViGEmBus GitHub](https://github.com/nefarius/ViGEmBus)
- 3Dconnexion's architecture is explicitly described (for the one app where Autodesk documented it) as the driver supplying raw navigation *data* while the host CAD app does its own navigation math/interpretation — i.e., pattern (c), direct SDK/API hook, is what gives an app full semantic control over how continuous analog data is interpreted (e.g., knowing "this is a rotation delta," not "this is a mouse-move pixel delta") — [Autodesk Fusion 360 blog](https://www.autodesk.com/products/fusion-360/blog/fusion-360-3dconnexion-spacemouse-integration/)
- Every hobbyist/general-purpose tool found in this research (JoyToKey, AntiMicroX's keyboard/mouse output mode, DS4Windows, Xpadder, the DIY Arduino/magnet CAD controllers) instead uses pattern (a): daemon + synthetic keyboard/mouse injection, which inherently reduces continuous analog signals (joystick tilt, trigger pressure) down to either discrete key events or raw mouse-delta pixels — losing the semantic richness that a native SDK hook like 3Dconnexion's would preserve

### Inferences
- For a DS4→CATIA V5 bridge on Windows, pattern (c) (true API/SDK hook) is not realistically available, since CATIA V5 does not expose a public API surface for arbitrary third-party input devices (only 3Dconnexion has that privileged native integration). That leaves a choice between (a) background daemon + synthetic mouse/keyboard injection via `SendInput`-class APIs, and (b) background daemon + virtual HID/XInput device (e.g., via a vJoy-style driver, or exposing the DS4 as a virtual 3Dconnexion-compatible device if that were technically feasible — no precedent for the latter was found).
- Given that CATIA V5 is a desktop CAD tool, not a game with kernel-level anti-cheat, the SendInput-detectability concerns that dominate the gaming-oriented search results are largely *not* a relevant risk for this project — this materially changes the tradeoff calculus versus a gaming-input-remapping context: pattern (a) (simple daemon + SendInput/mouse-move injection) is almost certainly sufficient and is exactly the approach every CAD-navigation hobbyist project already used successfully.
- The main real tradeoff for a CATIA project is not detectability but **semantic fidelity**: SendInput-style mouse-delta injection treats all motion as flat 2D pixel deltas and all buttons as discrete key-up/key-down, so a background daemon must do its own translation of analog stick tilt into incremental mouse movement (polled on a timer/loop) and must decide how to map trigger pressure or touchpad swipes into zoom, rather than CATIA ever being "aware" of the controller's raw 6-DOF-like character the way the 3Dconnexion plugin is.

### Gaps
- No controlled, up-to-date benchmark comparing SendInput-style injection vs. virtual-HID-driver injection specifically for *latency* in a CAD-navigation (not gaming) context was found; the available sources focus on gaming anti-cheat detectability, not raw input latency figures, so latency comparisons in this report are inferential, not measured.
- No example was found of anyone exposing a generic gamepad as a *virtual 3Dconnexion device* to piggyback on CATIA's native SDK plugin — it's unclear whether CATIA's 3Dconnexion plugin even validates device identity/HID descriptor strictly enough to make that spoofing approach technically possible; this remains an open, unresearched question.

## How do these tools structure user-facing configuration profiles (format, GUI, per-app switching, curves/deadzones, combos/chords, layers/shift-states)?

### Takeaway
The surveyed tools converge on a two-level profile hierarchy (a top-level "Profile" selects a game/app context; within it, one or more "Configs"/"Sets"/"Action Sets" hold the actual button-to-action mappings) with GUI-based remapping screens, support for switchable secondary mapping banks that function as shift-layers, and — at least for DS4Windows specifically — a rich analog-curve and deadzone system directly transferable to a DualShock4 project; however, no two tools use the same on-disk file format, and documented true multi-button chord support (as opposed to sequential macros or held-modifier shift-layers) was thin across all sources checked.

### Cited Findings
- reWASD's hierarchy: **Profile = one game/app context, holding one or more Configs = actual mapping layouts**; profiles switch via system tray, hotkey, or automatically per detected running title — [reWASD blog: "How to Remap Any Controller on PC"](https://www.rewasd.com/blog/post/how-to-remap-any-controller-on-pc-complete-guide)
- Steam Input's hierarchy: **Action Sets = full control schemes** (e.g., menu vs. gameplay), defined in a developer-authored VDF/IGA text file; **Action Set Layers = partial overlays** stacked on an active Action Set for small contextual tweaks, functioning as a true layering/shift-state system; action identifiers must be globally unique across the whole file even across different sets, a documented gotcha — [Steamworks: Steam Controller concepts](https://partner.steamgames.com/doc/features/steam_controller/concepts); [Steamworks: IGA file reference](https://partner.steamgames.com/doc/features/steam_controller/iga_file)
- AntiMicroX's hierarchy: one gamepad can hold multiple switchable numbered "Sets" (0-indexed internally, 1-indexed in UI, nameable), selectable via its GUI or externally over D-Bus (`setCurrentSet`-style control), plus an "auto profile" mode that switches profile sets automatically based on which application window currently has focus (X11/Windows only — not supported under Wayland) — [AntiMicroX README](https://raw.githubusercontent.com/AntiMicroX/antimicrox/master/README.md)
- JoyToKey's hierarchy: up to 16 switchable top-level profiles, plus within a profile a secondary "virtual joystick" mapping bank reachable by holding a designated shift button — a classic held-button shift-layer — [search summary of JoyToKey documentation/changelogs]
- DS4Windows's per-stick analog pipeline (directly reusable reference for DS4 projects): deadzone, then an "anti-deadzone" floor value (minimum output once past the deadzone, to avoid feeling "dead" near center), then a selectable output curve — Linear, Enhanced Precision, Quadratic, Cubic, two ease-out variants, or a fully custom curve drawn as a Bezier spline in a companion web-based editor — configured per-axis in a profile's Axis Config tab — [DS4Windows: Controller Deadzone docs](https://ds4-windows.com/?p=2670)
- DS4Windows macro system: a "Special Actions" tab lets the user pick a trigger button and record an arbitrary sequence of key presses as a macro; a known limitation is that if two macros are triggered simultaneously, the longer one gets cut off when the shorter one finishes, rather than both running independently to completion — [PCSX2 forum thread](https://forums.pcsx2.net/Thread-DS4Windows-J2K?page=61)
- All of the GUI-based tools reviewed (reWASD, AntiMicroX, JoyToKey, DS4Windows) use a visual remapping screen (an on-screen controller diagram or tabbed settings panel) rather than requiring users to hand-edit config files directly, though AntiMicroX does also support scripted/headless control via D-Bus for advanced/automated use — [AntiMicroX README](https://raw.githubusercontent.com/AntiMicroX/antimicrox/master/README.md)

### Inferences
- For a DS4→CATIA V5 project, the most directly reusable prior art for the *analog input pipeline* (deadzone → anti-deadzone floor → selectable response curve, including a custom Bezier option) is DS4Windows's own system, since it already solves exactly the DualShock4-specific problem of turning imprecise stick/trigger/touchpad data into smooth, controllable continuous output, and a Bezier/curve-based "feel" control is likely to transfer well to tuning CATIA navigation speed (e.g., orbit sensitivity, zoom rate).
- The "Profile → sub-layer" pattern (reWASD's Profile/Config, Steam Input's Action Set/Action Set Layer, JoyToKey's profile/virtual-joystick-shift, AntiMicroX's numbered Sets) is consistent enough across independent tools to be treated as a validated design convention: a CATIA bridge should likely implement (1) a top-level Profile keyed to the active CATIA workbench or mode (e.g., Sketch, Part Design, Assembly, DMU navigation) and (2) one or more shift/held-button layers within each profile for secondary commands, rather than inventing a flatter or more exotic scheme.
- True simultaneous multi-button chord detection (as distinct from "hold one button as a shift/layer key") was not clearly documented as a first-class feature in any tool surveyed; this suggests chord support, if needed for the CATIA project, may require custom logic rather than being modeled directly off an existing tool's chord implementation.

### Gaps
- Exact on-disk file formats were not confirmed for several tools: JoyToKey's and Xpadder's own documentation did not clearly state JSON/XML/INI in the sources retrieved (only "Joystick Gremlin Ex," a related-but-different tool, was confirmed to use XML); AntiMicroX's README pointed to a separate community profile repository rather than documenting the format inline. A project team wanting an authoritative format reference should inspect actual sample profile files from each tool's install/profile directory directly rather than relying on documentation alone.
- No source clearly documented a dedicated "combo/chord" (simultaneous multi-button, non-shift) feature with its own named UI section in any of the five tools surveyed (JoyToKey, AntiMicroX, reWASD, Steam Input, DS4Windows) — this may exist but was not surfaced in the search results reviewed, and should be treated as an open gap rather than confirmed absent.
