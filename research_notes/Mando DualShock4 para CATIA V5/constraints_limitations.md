# Technical Constraints and Limitations: DualShock4-to-CATIA V5 Control App (Windows)

## Key Question 1: Does CATIA V5's COM Automation API behave differently or have restrictions inside a VM (VMware/Hyper-V/Citrix/VDI/RDP) versus bare metal?

### Takeaway
There is no authoritative, CATIA-V5-specific documentation confirming or denying COM/input behavior differences inside VMs — this is a significant **gap**. What's well documented is adjacent and strongly suggestive: (a) licensing/virtualization support is explicitly restricted by Dassault for some license types, (b) Citrix blocks custom automation channels by default on recent versions, and (c) remote-desktop/VDI sessions are generally not recommended by Dassault partners for production CATIA work. All of this implies real risk, but the specific COM-automation-inside-a-VM behavior itself is inferred, not confirmed.

### Cited Findings
- A Parallels (not VMware, but similar dongle-licensing architecture) knowledge base article states virtual machines are **not supported** according to the Dassault Systèmes (DS) License Server documentation. — [Parallels KB](https://kb.parallels.com/en/124658)
- A hosting-provider blog (secondary source, not Dassault itself) states that a node-locked CATIA seat will not launch over a standard Remote Desktop session, and that network/floating licensing from a DSLS server is the usual workaround; it also states that Dassault partner **Inceptra does not recommend Remote Desktop for production CATIA work**, considering it better suited to light parts, small assemblies, or review tasks. — [AceCloudHosting blog](https://www.acecloudhosting.com/blog/run-catia-remotely/)
- IBM support notes (for CATIA-adjacent SmarTeam COM integration, not CATIA V5 core) describe COM-based scripts failing to reach a session, with `GetObject` failing when "the Windows message stack is full," and IBM explicitly calling this "a limitation of using the Windows COM technology" itself (i.e., not VM-specific, but a general Windows COM/message-pump fragility that would be exacerbated under remoting). — [IBM Support](https://www.ibm.com/support/pages/node/5263095)
- UiPath's own documentation states that starting with **Citrix Virtual Apps and Desktops 7 2109, all custom virtual channels are blocked by default**, which breaks UiPath's Remote Runtime communication inside Citrix sessions unless re-enabled by policy. This is a general Citrix security hardening change, not CATIA-specific, but it is directly relevant to any custom automation/input-injection tool trying to operate inside a Citrix HDX session. — [UiPath Docs](https://docs.uipath.com/studio/standalone/latest/user-guide/automating-citrix-technologies)
- Microsoft's own troubleshooting documentation acknowledges that recording/synthetic-input tools (e.g., Power Automate Desktop) generally **cannot record/operate correctly inside VDI environments such as Citrix or RDP** sessions — a generic Windows automation limitation, not CATIA-specific, but applicable to any UI-automation approach layered on a remote session. — [Microsoft Learn](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/cannot-record-in-vdi-environments)
- One vendor source (secondhand) states Dassault does publish certified configurations for VDI, and that the typical delivery layer for CATIA-on-VDI is **Citrix HDX 3D Pro**, which renders on a server-side GPU and streams the framebuffer to the client. — [AceCloudHosting blog](https://www.acecloudhosting.com/blog/run-catia-remotely/)
- Citrix's own documentation on generic USB redirection lists **game controllers among typical Human Interface Devices (HIDs)** that can be redirected, but notes that "some USB devices do not operate correctly with generic USB redirection," and that optimized (non-generic) redirection is preferred where available; no CATIA- or gamepad-specific tested list was found. — [Citrix Docs](https://docs.citrix.com/en-us/citrix-virtual-apps-desktops/2203-ltsr/general-content-redirection/usb.html)

### Inferences
- If the DS4 app and CATIA V5 are both running *inside* the same VM/VDI session (the more likely target architecture, since the controller would need to be USB-redirected into the VM anyway), then COM automation between two in-guest processes should behave like any two Windows processes on one desktop — the VM layer itself shouldn't change COM semantics. The bigger risks are (a) licensing refusing to run at all in a VM without an explicitly supported configuration, and (b) GPU/OpenGL rendering degradation (see Q2/general), not COM per se.
- If the controller is physically on the user's client device and must reach a CATIA instance running remotely (Citrix/VDI), the input must first survive **USB/HID redirection** (generic USB redirection, policy-gated, and explicitly flagged as unreliable for "some USB devices") before any in-VM software ever sees it — this is a separate, non-trivial failure point from COM automation itself.
- Because Citrix blocks custom virtual channels by default on recent Virtual Apps and Desktops versions, a custom architecture that tries to tunnel HID data to the guest via its own virtual channel (rather than generic USB redirection) would likely need an explicit Citrix policy change from the IT admin — a non-trivial, enterprise-IT-gated requirement.
- Window-handle/focus behavior for synthetic input (see Q3) is likely to be **more fragile, not less**, inside an RDP/Citrix session, because the remote session's foreground/focus state is itself virtualized and may not track 1:1 with what the host recognizes as "foreground" — but no direct source confirms this for CATIA specifically.

### Gaps
- No Dassault Systèmes or Citrix documentation was found that directly discusses COM Automation API behavior, window-handle stability, or synthetic-input delivery for CATIA V5 specifically when running inside a VM/Citrix/VDI session. This is the single largest unresolved question in this research area and should be flagged to the user as needing direct vendor confirmation or empirical testing in the target VDI environment.
- No data found on Hyper-V specifically (most available discussion concerns VMware/Parallels/Citrix).

## Key Question 2: What license/version is required to use CATIA V5's Automation API — is it included in a base seat, or does it need Knowledgeware/CAA, and is VBA affected by Microsoft's broader VBA deprecation?

### Takeaway
No official Dassault Systèmes document was found that explicitly states the license tier required for the Automation (COM/VBA) API. The best available evidence (a third-party technical blog, partially corroborated by a Dassault CAA licensing PDF) indicates the **Automation API (VBA/VB.NET/VBScript/Python scripting via COM) requires only a base CATIA license**, while **Knowledgeware/EKL requires a separate KW Advisor or Expert module license**. Separately, there is no confirmed Dassault announcement that VBA support in CATIA V5 itself is being deprecated, though there is a live, unresolved community question about whether Microsoft's VBScript deprecation will collaterally affect VBA-based CAD macros, and historical IBM support tickets show VBA has had version-to-version breakage before.

### Cited Findings
- A third-party CATIA customization guide states that Automation Object scripting (VBA, VB.NET, VBScript, Python) "requires only a base CATIA license," and separately lists Knowledgeware/EKL as needing a KW Advisor or Expert module license. — [qdchenshi.pages.dev guide](https://qdchenshi.pages.dev/en/blog/2025/catia-development-guide-en) *(third-party, not an official Dassault source — treat as informed claim, not confirmed fact)*
- A Dassault Systèmes licensing document (CAA licensed program specification) states that **COM is included in any CATIA Configuration** — this partially corroborates the claim that the Automation/COM interface is not gated behind a separate paid add-on. — [3DS CAA V5R18 Licensed Program Specification (PDF)](https://www.3ds.com/assets/Terms/LicensedProgramSpecifications/CATIA/CAA_V5R18.pdf)
- The **CAA RADE (Component Application Architecture)** — the compiled C++ SDK for deep CATIA extension/plugin development — is a *separate* licensed product from basic VBA/Automation scripting; a PTC community thread and a German-language PTC support article both raise (without a confirmed public answer) the question of whether a CAA RADE license is a sufficient/necessary license configuration for certain integration scenarios, implying CAA RADE and basic Automation licensing are treated as distinct by Dassault/PTC. — [PTC Community](https://community.ptc.com/t5/Windchill/CATIA-WGM-CAA-License/td-p/305930), [PTC Support Article](https://www.ptc.com/de/support/article/CS197589?as=0)
- IBM support tickets document that VBA macro functionality has broken across CATIA V5 releases before — e.g., VBA macro/VB editor options reported greyed out in CATIA V5 R8 SP1 (closed by IBM as unreproducible), and multiple failures attributed by IBM to "CATIA Library Re-organization" across releases, requiring "manual adjustments to existing VB/VBA projects" and unchecking references to type libraries that became obsolete. — [IBM Support HC91720-class tickets](https://www.ibm.com/support/pages/apar/HD45749)
- Some VBA/VBScript interaction issues are classified by IBM as **permanent restrictions** rather than bugs to be fixed — e.g., a VBA event-handling issue triggered when a VBScript macro launches a VBA form, which IBM attributes to "the Microsoft VBA code" itself being the root cause, recommending a workaround (write a VBA macro directly) rather than a fix. — [IBM Support](https://www.ibm.com/support/pages/apar/HD25903)
- A Dassault community article confirms an active, ongoing **migration path away from VBA toward 3DEXPERIENCE services**: "Many VBA V5 processes were replace[d] by 3DExperience services, and several features were cancel[ed] or modified." (Part 1 of a series; grammar as in source.) — [3DSWYM CATIA community post](https://3dswym.3dexperience.3ds.com/post/catia-user-community/transition-steps-to-adapt-vba-apps-from-v5-to-3dx-daniel-dobrzynski-part-1_aLy34MX1T2edfHLC9mwXpw)
- A live, **unresolved** community question (SIMULIA/CST Studio Suite context, not CATIA directly, but same underlying Microsoft VBA/VBScript engine concern) explicitly asks "whether Dassault Systèmes has issued any official guidance on" the impact of **Microsoft's VBScript deprecation** on VBA macros in Dassault products — the thread shows no official answer was given. — [3DSWYM community question](https://3dswym.3dexperience.3ds.com/question/simulia-community/impact-of-vbscript-deprecation-on-cst-studio-suite-vba-macros_IzOGxJAvTfOxd2ne1aJusg)
- Dassault has confirmed, separately, that it is **discontinuing Support Services for Windows 10** after October 14, 2025 "in accordance with our Support Services Policy," pushing customers to Windows 11 on certified configurations — relevant context for long-term platform support but not specific to VBA/Automation licensing. — [Technia](https://www.technia.com/end-of-support-for-windows-7-and-8-announced-with-next-release-of-3dexperience/)

### Inferences
- Taken together, the evidence suggests a **base CATIA V5 seat most likely includes enough COM/Automation access to drive the app via VBA/VB.NET/Python** without purchasing Knowledgeware or CAA RADE — but this rests on a single non-Dassault blog plus one supporting licensing PDF snippet, not an explicit Dassault statement, so it should be verified directly with the organization's Dassault reseller/License Compliance team before relying on it for rollout planning.
- Microsoft's industry-wide deprecation of VBA/VBScript (well documented generally, though not independently re-confirmed in this research pass) is a long-term risk to any CATIA V5 VBA-based integration, but there is no evidence found that it has yet broken CATIA V5 automation; Dassault's own migration messaging (pushing users toward 3DEXPERIENCE services) suggests VBA in V5 is a legacy, declining-investment path rather than an actively-deprecated/blocked one as of this research.
- Given documented history of VBA breaking across CATIA V5 service packs/releases (library reorganization, type-library reference breakage), any VBA-based integration should be treated as **release-level-fragile** — code tested on one R20xx release/service pack is not guaranteed to run unmodified on another.

### Gaps
- No official Dassault Systèmes statement was found naming the exact license SKU/tier required for the CATIA V5 Automation (COM) API.
- No confirmed information found on whether specific CATIA V5 release levels (V5-6R2015 through R2021/R2022x) differ in automation *capability* (vs. just bugfixes) — this needs direct release-note review or vendor confirmation.
- No confirmed Dassault announcement of VBA being dropped/disabled in CATIA V5 specifically (only adjacent, unresolved community concern about Microsoft's VBScript deprecation, and general migration-to-3DEXPERIENCE messaging).

## Key Question 3: Does synthetic input (SendInput/PostMessage/SendMessage) reliably reach CATIA V5's window(s) without true foreground focus?

### Takeaway
This is the best-documented area of the research. Microsoft's own documentation and a Microsoft engineer's (Raymond Chen) public statements are consistent and authoritative: **SendInput requires the target window to actually have keyboard focus/be foreground** (it injects into whatever has focus, not a specified HWND), and both SendInput and PostMessage-based keyboard/mouse events are subject to **UIPI (User Interface Privilege Isolation)**, which blocks input from a lower-integrity-level process to a higher-integrity-level one. PostMessage can deliver messages to a background window's queue without stealing focus, but it is **not a reliable way to simulate real keyboard input** for most applications (Chen: "you can't simulate keyboard input with PostMessage," though some poorly-written apps can be fooled). No CATIA-V5-specific test was found, but circumstantial CATIA V5 VBA community evidence (SendKeys/clunky keystroke simulation complaints) is consistent with CATIA requiring true focus/SendInput-style input rather than accepting raw PostMessage.

### Cited Findings
- Microsoft's official `SendInput` documentation states the function is **subject to UIPI**: "applications are permitted to inject input only into applications that are at an equal or lesser integrity level," and a blocked call fails silently — "neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking." — [Microsoft Learn: SendInput](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-sendinput)
- SendInput targets **whatever window currently has focus** system-wide, not an arbitrary HWND passed by the caller — meaning a background/non-focused target application cannot receive SendInput events at all without first being brought to the foreground. — [Community/forum consensus corroborating MSDN semantics](https://cplusplus.com/forum/windows/187360)
- Raymond Chen (Microsoft, "The Old New Thing" developer blog) states plainly: **"you can't simulate keyboard input with PostMessage,"** though he notes "there are indeed many programs that can be fooled by this trick" and that he "once came across an application where I could simulate keyboard input via PostMessage only if it had keyboard focus" — i.e., even the exception required focus. — [Microsoft DevBlogs: The Old New Thing](https://devblogs.microsoft.com/oldnewthing/20160715-00/?p=93885)
- PostMessage places messages directly in a target window's message queue without requiring focus, but does **not update global keyboard state** (e.g., `GetAsyncKeyState`, `GetKeyState` won't reflect it), making it unreliable for apps that check real key state rather than just processing WM_KEYDOWN/WM_KEYUP messages; PostMessage keyboard/mouse simulation is also itself subject to UIPI — a lower-privilege sender cannot post synthetic input messages to a higher-privilege (e.g., elevated/Administrator) target window. — [Microsoft Learn: SendMessage, PostMessage, and Related Functions](https://learn.microsoft.com/en-us/windows/win32/wintouch/sendmessage--postmessage--and-related-functions)
- A Microsoft Q&A thread on sending keystrokes to a non-focused app reports the practical experience that "the receiving app has to be active" for input simulation to be reliably accepted. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/496305/send-keystroke-to-another-app-without-focus)
- Indirect CATIA V5 evidence (eng-tips.com forum, CATIA VBA automation context): a user reports "using sendkeys in the VBA Excel macro to send the commands to V5 is very clunky," and another reports `SendKeys {"ENTER"}` failing when a dialog first appears — consistent with CATIA's UI requiring true focus for keystroke simulation to land reliably, though these are forum reports, not a controlled test. — [Eng-Tips forum threads](https://www.eng-tips.com/threads/how-to-execute-catia-v5-macro-from-excel-vba.208000)
- Dassault/IBM's own CATIA documentation recommends **avoiding keystroke/dialog injection entirely** in favor of driving CATIA through its native Automation object model: IBM notes the `StartCommand` VBA method "is useful to execute one-shot (not interactive) commands [but] is not safe for interactive commands" — implying Dassault's own guidance steers developers away from synthetic-input tricks and toward object-model calls wherever the API exposes them. — [IBM Support](https://www.ibm.com/support/pages/node/5076111)
- One conflicting/unverified claim (DEV Community blog, not corroborated elsewhere) asserts keyboard events via SendInput *can* reach elevated apps from a lower-privilege sender, "only window messages are blocked" — this directly contradicts Microsoft's own SendInput documentation on UIPI and should be treated as unreliable/unverified. — [DEV Community (unverified, conflicts with MSDN)](https://dev.to/howmindswork/how-i-inject-text-into-any-windows-app-including-elevated-processes-4jl6)

### Inferences
- A practical architecture implication: the DS4-to-CATIA app will most likely need to **bring CATIA's window to the real foreground and use SendInput** (true focus-based injection) for reliable keyboard/mouse-equivalent commands, rather than relying on PostMessage to a background CATIA window — this matches both the general Windows input-injection literature and the CATIA-specific forum complaints about SendKeys being "clunky."
- Wherever possible, the design should **prefer calling CATIA's COM Automation API directly** (object model calls) over synthetic keyboard/mouse injection for any command that has an Automation equivalent — this sidesteps UIPI, focus-stealing, and CATIA's apparent sensitivity to non-focused/queued input entirely, and is explicitly the direction Dassault's own documentation steers developers for interactive operations.
- If CATIA V5 and the controller app run at different Windows integrity levels (e.g., CATIA launched "as Administrator" per some corporate deployment images, while the DS4 app runs as standard user), **UIPI will silently block all synthetic input** regardless of method — this is a realistic enterprise deployment risk (locked-down images often auto-elevate certain engineering apps) and should be explicitly tested in the target environment.

### Gaps
- No controlled/documented test of SendInput or PostMessage specifically against a CATIA V5 window (MFC-based or Dassault proprietary CPNext/toolkit panels) was found; all CATIA-specific evidence is indirect (VBA SendKeys community complaints) rather than a direct Win32-level test.
- No confirmed information on whether CATIA V5's 3D viewport/dialogs are standard Win32/MFC controls (which generally respond better to WM_* messages) versus custom-drawn Dassault UI toolkit elements (which may ignore synthetic WM_LBUTTONDOWN/WM_KEYDOWN entirely regardless of focus) — this is architecturally important and unresolved.

## Key Question 4: Does raw HID access to a DS4 controller, and installing HidHide/ViGEmBus, require admin rights or special permissions, and would this be blocked in a locked-down corporate environment?

### Takeaway
Installing kernel-mode driver components (HidHide, ViGEmBus) **requires Administrator rights** and a properly (production-)signed 64-bit kernel driver — confirmed by Microsoft's own driver-signing documentation and by the projects' own release practices. Reading the DS4 via plain user-mode **Raw Input** (no virtual driver) does **not** appear to require elevation based on example code found, though no authoritative Microsoft statement confirms this explicitly. Separately, standard Windows Group Policy / Intune "Device Installation Restrictions" and USB-class-based device-control policies (confirmed via Microsoft and Intune docs) can block HID-class (including game controller) devices enterprise-wide, and such policies are explicitly documented as a real risk in corporate-managed images.

### Cited Findings
- Microsoft's own driver documentation states a kernel-mode driver **must be signed to load on 64-bit Windows Vista and later**; unsigned/test-signed drivers only load if "test signing" is explicitly enabled, which itself **requires Administrator rights** to turn on, and "by default, Windows does not load test-signed kernel-mode drivers." — [Microsoft Learn: The TESTSIGNING Boot Configuration Option](https://learn.microsoft.com/hu-hu/windows-hardware/drivers/install/the-testsigning-boot-configuration-option)
- ViGEmBus ships **pre-built, production-signed binaries** for Windows 10/11 via an official installer (Nefarius Software Solutions e.U.), avoiding the need for test-signing mode in normal use; older/unsigned builds required test mode or self-signing. — [ViGEmBus GitHub](https://github.com/ViGEm/ViGEmBus)
- HidHide is described (third-party summary, not the primary README directly retrieved) as an open-source **kernel-mode filter driver** plus a user-mode companion app; the filter driver "starts automatically and runs unattended with system privileges," a system reboot may be triggered after install/removal, and — notably — the **configuration utility itself runs without elevation**, implying elevation is required only for the driver install step, not day-to-day use. — [Third-party HidHide summary](https://best-of-web.builder.io/library/nefarius/HidHide) *(primary HidHide GitHub README was not directly fetched in this pass — treat driver-install-admin-requirement as a reasonable inference corroborated by general kernel-driver-signing rules above, not a directly-quoted HidHide statement)*
- A public example (gist) implementing DualShock4/DualSense reading via Windows **Raw Input** (`RegisterRawInputDevices`/`WM_INPUT`), identifying the controller by vendor/product ID and parsing raw HID report bytes, shows **no elevation request** in the approach — suggesting plain Raw Input HID reads of a DS4 do not inherently require admin rights on a standard (non-locked-down) Windows installation. — [Public gist example](https://gist.github.com/mmozeiko/c136c1cfce9fe4267f3c8f7b90f8e4d4)
- Native Windows HID/game-controller recognition of DS4 is **inconsistent** across reports: one unverified 2026 guide claims native DualSense HID support was added around Windows 10 21H2, but a Microsoft Q&A thread reports a wired DS4 **not** being recognized as an "HID Compliant Game Controller" out of the box — implying native support, where it exists, is inconsistent/model- and connection-dependent, and third-party drivers (DS4Windows, DsHidMini, etc.) remain commonly used. — [Microsoft Q&A thread (DS4 not recognized)](https://learn.microsoft.com/en-au/answers/questions/5648598/how-to-fix-ps4-controller-not-working)
- Microsoft's Group Policy documentation ("Manage Device Installation with Group Policy") confirms organizations can **allow or block device installation by hardware/device ID**, and Microsoft's own Defender for Endpoint device-control guidance explicitly warns that admins must be careful to allowlist the IDs for keyboards/mice "or users can lose access to their machine" when applying such block policies — confirming these policies are real, used in managed enterprise fleets, and operate at a granularity that could target DS4's HID vendor/product ID or the HID device class broadly. — [Microsoft Learn: Manage Device Installation with Group Policy](https://learn.microsoft.com/en-us/windows/client-management/manage-device-installation-with-group-policy); [Microsoft Tech Community: Defender for Endpoint Device Control](https://techcommunity.microsoft.com/blog/microsoftdefenderatpblog/device-control-device-installation-update/2734428)
- Microsoft Intune's Administrative Templates / Settings Catalog documentation confirms **USB restriction policies are commonly deployed to block classes of USB devices** (e.g., flash drives, cameras) while allowlisting specific ones (e.g., keyboard/mouse); since HID game controllers fall under the generic HID device class (USB base class 03h), a class-based restriction policy not specifically written to exempt game controllers could incidentally block a DS4. — [Microsoft Intune docs](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/restrict-usb), [Intune Administrative Templates: Restrict USB](https://learn.microsoft.com/nb-no/mem/intune/configuration/administrative-templates-restrict-usb)

### Inferences
- In a **simple single-user Windows PC** scenario (no corporate MDM/GPO), installing HidHide/ViGEmBus will prompt a standard UAC elevation (expected, one-time, during install) but should otherwise work without special configuration, and a user-mode Raw-Input-only approach (no virtual driver) may avoid even that.
- In a **locked-down enterprise-managed Windows image**, three independent IT controls could each block this app's core functionality, and all three are plausible in an engineering/manufacturing enterprise: (1) users may lack local admin rights at all, blocking any driver installation outright; (2) Device Installation Restriction GPOs/Intune policies could block the DS4's USB HID device ID or class; (3) application/driver allowlisting (e.g., WDAC, AppLocker, or EDR-based execution control) could block an unsigned or newly-introduced signed driver from an unapproved publisher. This should be treated as a **go/no-go gating risk** to validate with the target organization's IT/security team before rollout, not an afterthought.
- Preferring a design that avoids installing *any* kernel driver (plain Raw Input/HID API reads of the physical DS4, with no virtual-controller remapping) substantially reduces the admin-rights and driver-signing attack surface and is likely the most enterprise-deployment-friendly architecture, at the cost of losing ViGEmBus/HidHide's "hide the real device" ghost-input mitigation (see Q5) if a virtual controller is not also created.

### Gaps
- No direct confirmation that plain Raw Input HID access to a DS4 is admin-free on Windows 11 was found from an authoritative Microsoft source (only inferred from example code lacking elevation logic).
- No information found specific to whether HidHide/ViGEmBus drivers are commonly pre-approved/allowlisted in typical corporate WDAC/AppLocker/EDR policies, or how often IT departments deny such installs in practice — this would require direct sysadmin-forum or case-study evidence not surfaced in this research pass.

## Key Question 5: Are there known DS4 Bluetooth pairing/driver-conflict reliability issues on Windows, and what's the standard way to avoid ghost/double input?

### Takeaway
This is well documented in the DS4Windows community/project documentation: **double/"ghost" input is a known, common problem** caused by Windows' built-in HID gamepad driver and a custom tool (e.g., DS4Windows) both reading the same physical controller simultaneously, each exposing it as a separate input device to applications. The documented, recommended fix is to **hide the physical controller from other applications using HidHide**, exposing only a single virtual controller (e.g., via ViGEmBus) to downstream consumers. The DS4Windows project also states **only the Microsoft Bluetooth stack is supported**, implying third-party/vendor Bluetooth stacks are a known source of additional unreliability.

### Cited Findings
- DS4Windows's own documentation identifies the root cause directly: **"Windows sees the real controller and DS4Windows's virtual controller at the same time,"** and states the main/recommended fix is to **hide the physical controller** so that only the virtual controller is visible to games/applications. — [DS4Windows Docs: In-game problems](https://schmaldeo.github.io/DS4WindowsDocs/docs/troubleshooting/ingame)
- HidHide is explicitly named as **"the recommended method"** for this hiding step, with a matching toggle present directly in DS4Windows's settings tab. — [DS4Windows Docs](https://schmaldeo.github.io/DS4WindowsDocs/docs/troubleshooting/ingame)
- A third-party troubleshooting guide adds operational detail: if DS4Windows stops seeing the controller after hiding is enabled, the fix is to temporarily disable hiding in the HidHide client, reconnect the controller, then re-enable hiding; it also notes **both the USB and Bluetooth hardware IDs of the same physical controller need to be configured for hiding** if the device is used over both connection types. — [Technobezz guide](https://www.technobezz.com/how-to-fix-ds4windows-not-working/)
- Leftover drivers from older tools (e.g., **ScpToolkit**) are flagged by the DS4Windows community as a separate common cause of Bluetooth conflicts — users who previously used ScpToolkit may need to **uninstall its drivers** before DS4 Bluetooth works correctly with a newer tool. — [DS4Windows Docs](https://schmaldeo.github.io/DS4WindowsDocs/docs/troubleshooting/bluetooth)
- The DS4Windows project states **"only use of [the] Microsoft [Bluetooth] stack is supported"** — i.e., third-party Bluetooth dongle/stack software (e.g., some Broadcom/Toshiba stacks bundled with older BT dongles) is a known source of unsupported, unreliable behavior. — [DS4Windows Docs](https://schmaldeo.github.io/DS4WindowsDocs/docs/troubleshooting/bluetooth)
- Some games that have **native DS4 support built in** can read the controller directly in parallel with other software, which the documentation flags as a possible cause of double input "even when DS4Windows isn't in use" — i.e., ghost/double input is not exclusively a DS4Windows-vs-Windows-driver problem; any two consumers reading the same physical HID device concurrently can cause it, which is directly relevant to a custom CATIA-control app that reads the DS4 raw while Windows' default XInput/HID gamepad driver is also active. — [DS4Windows Docs](https://schmaldeo.github.io/DS4WindowsDocs/docs/troubleshooting/ingame)

### Inferences
- For the DS4-to-CATIA app specifically, since CATIA itself has **no native gamepad support** to conflict with, the "double input" risk is lower than in a gaming context (there's no second consumer parsing XInput state for CATIA's UI) — but if the custom app also exposes a virtual XInput/DirectInput device (e.g., so the physical DS4 can *also* still be used for something else, or for diagnostics), the same double-exposure risk documented for DS4Windows would apply, and the same HidHide-based "hide-the-physical-device" mitigation pattern should be reused.
- If the architecture is "raw HID read only, no virtual controller created, no SendInput-based secondary exposure," ghost input risk is likely minimal by construction, since the DS4 is the only consumer of its own data and nothing else in Windows is set up to also interpret it as a generic game controller for any visible UI purpose.
- Bluetooth pairing reliability (dropped connections, latency, re-pairing issues) is well-documented as a recurring community pain point for DS4-on-Windows generally (implied by the volume and specificity of the DS4Windows troubleshooting documentation dedicated to it), reinforcing that a **wired USB connection should be the recommended/default configuration** for a reliability-sensitive engineering-tool use case, with Bluetooth offered only as a secondary/optional mode.

### Gaps
- No quantitative data (failure rates, latency figures) on DS4 Bluetooth reliability on Windows was found — only qualitative community troubleshooting documentation confirming the problem class exists and the standard mitigation.
- No source specifically addresses ghost-input risk in a non-gaming, single-custom-consumer context (i.e., this inference is reasoned from the documented gaming-context root cause, not independently confirmed).

## Key Question 6: Would corporate antivirus/EDR likely flag this app (HID reading + synthetic input injection + COM automation), and how do legitimate tools like AutoHotkey avoid false positives?

### Takeaway
Yes — this is well documented as a real and current problem. **AutoHotkey has a long, extensively documented history of antivirus false positives**, and several **major EDR platforms (Carbon Black/VMware, Palo Alto Cortex XDR) have explicit, named detection rules specifically for `SetWindowsHookEx`-based keylogger-like behavior** — a close technical analog to synthetic-input tooling. Carbon Black's own knowledge base confirms a **2025 rule update (25v3) specifically added detections for this API pattern**, actively breaking previously-trusted software. The documented mitigations are process-based (vendor false-positive submission, hash/binary allowlisting, exclusion rules) rather than purely preventive; code signing is "generally" believed to help build reputation but was **not confirmed by any source found** to reliably prevent these specific heuristic/behavioral flags.

### Cited Findings
- AutoHotkey's own official site explicitly acknowledges the problem and gives guidance: **"the best thing you can do if you encounter a possible false positive is submit the executable file to your antivirus vendor for analysis,"** and states plainly that "most often these alerts are false positives, meaning that the antivirus program is mistaken." — [AutoHotkey Safe Browsing page](https://autohotkey.com/download/safe.htm)
- A recent (2023) Bitdefender community thread shows the problem is ongoing and current, not merely historical: **"latest Bitdefender [update, 27 Nov 23] blocks ahk2exe from compiling Autohotkey scripts."** — [Bitdefender Community](https://community.bitdefender.com/en/discussion/97997/latest-bitdefender-27-nov-23-blocks-autohotkey-compilation)
- Carbon Black's own knowledge base (Broadcom) confirms that starting after **June 2025**, high-severity alerts began appearing against previously-trusted, known-good software, because **"Carbon Black Cloud rules were updated in 25v3 to include detections for API calls that can be used as a keylogger"** (i.e., `SetWindowsHookEx`-pattern detections) — this is a vendor-acknowledged, dated, confirmed rule change, not speculation. The documented remedy is to confirm the software's behavior with the vendor, then "approve the hash" or add a process-specific exclusion. — [Broadcom/Carbon Black Knowledge Base](https://knowledge.broadcom.com/external/article/403731/severity-7-alerts-seen-indicating-called.html)
- Palo Alto's Cortex XDR documentation has a **named, productized analytic alert** — "Uncommon SetWindowsHookEx API invocation of a possible keylogger" — rated Medium severity, whose investigation guidance explicitly asks analysts to check "whether the process has a visible window, whether it is a known application recently updated, and whether it is built with AutoHotkey" — i.e., Palo Alto's own documentation names AutoHotkey-style tools as a recognized, expected source of these alerts requiring manual triage rather than automatic blocking. — [Palo Alto Cortex XDR Docs](https://docs-cortex.paloaltonetworks.com/r/Cortex-XDR-Analytics-Alert-Reference-by-data-source/Uncommon-SetWindowsHookEx-API-invocation-of-a-possible-keylogger)
- A real-world incident report (Microsoft Q&A) describes Carbon Black **actively blocking Microsoft's own Outlook and Excel** processes from calling `SetWindowsHookExW` on themselves, confirming these behavioral EDR rules can produce false positives even against first-party Microsoft software, not just small third-party tools. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1609068/code-injection-from-outlook-and-excel)
- A Microsoft engineer's reply to a Veracode static-analysis flag on `SetWindowsHookEx` acknowledges the dual-use nature directly: **"DLL injection can be used for legitimate purposes; however, it is also a common technique used by rootkits to execute malicious code."** — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1693583/veracode-error-with-setwindowshookex-win-api-call)
- No source found confirms that code signing by itself reliably prevents these specific behavioral/heuristic EDR flags (as opposed to static AV signature flags on an unsigned binary) — one automated scan report on an AutoHotkey installer noted it was unsigned "despite code signing being applicable," framed as a reputation/trust gap rather than a confirmed fix for the behavioral detections described above. — [MalwareTips automated scan](https://tools.malwaretips.com/file-scan/aca3f50a66ac4c6fcee5bd168c90929c70f3ea9e12fc62b6699a26ea1e087dc3)

### Inferences
- A DS4-to-CATIA app combining (a) low-level HID reads, (b) synthetic input injection (likely via `SetWindowsHookEx`-adjacent or `SendInput`/`PostMessage` APIs), and (c) COM automation of a third-party engineering application is a **very plausible target for exactly the kind of named EDR detections documented above** (Carbon Black's 25v3 keylogger-pattern rule, Cortex XDR's SetWindowsHookEx alert) — this combination of capabilities closely resembles the behavioral signature these tools are designed to catch, independent of actual intent.
- Given that even AutoHotkey — an extremely widely-used, long-established, broadly-trusted automation tool — still triggers ongoing false positives as of 2023+ despite years of reputation-building, **a brand-new, narrowly-distributed internal tool should expect to be flagged by default** on first deployment to any enterprise EDR, and the realistic mitigation path is **process-based** (working with the organization's security team in advance to pre-approve the hash/binary, add a scoped exclusion, or get the behavior reviewed) rather than purely technical.
- Code signing is likely still worth doing (it is standard practice and helps with static-signature-based AV, SmartScreen reputation, and WDAC/AppLocker allowlisting by publisher), but based on available evidence it should **not be assumed sufficient** on its own to prevent behavioral-EDR flags on the `SetWindowsHookEx`/input-injection pattern — those require explicit allowlisting regardless of signature.

### Gaps
- No source found specifically confirms or denies whether COM automation calls themselves (as opposed to HID reads or input injection) are commonly flagged by EDR — the research surfaced strong evidence only for the input-injection/hooking side of the behavior profile.
- No case study or vendor guidance found specifically for "how to get a custom internal engineering automation tool pre-approved by corporate EDR/IT security" — general advice (vendor submission, hash allowlisting) comes from the AutoHotkey/Carbon Black context and is extrapolated, not confirmed for this exact scenario.
